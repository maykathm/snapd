1 The big picture

What snapd is responsible for, and the one mental model that makes everything else in this page make sense.

In plain termssnapd is a background daemon plus a CLI (snap) and a few small sandbox helpers. It
  • installs snaps (read-only SquashFS images) by mounting them,
  • sandboxes every app and grants access to resources only through interfaces,
  • records every operation as a resumable list of tasks, so nothing is left half-done after a crash or reboot,
  • and, on Ubuntu Core, manages the whole device — kernel, boot, disk encryption, identity — because those are snaps too.

What snapd actually manages

snapd is a background daemon (plus a family of small helper binaries) that installs, updates, confines and runs snaps — self-contained, read-only SquashFS packages carrying an app or service plus metadata (chiefly meta/snap.yaml). Installing a snap is mostly "make this SquashFS file available by mounting it, then connect it safely to the rest of the system."

Beyond individual snaps, snapd can orchestrate the lifecycle of an entire device when every component of the system — root filesystem, kernel, bootloader config — is itself a snap. That's Ubuntu Core. Classic desktop/server snapd and Ubuntu Core snapd are literally the same binary and the same Go codebase; what differs is which snaps are installed (gadget/kernel/base vs. a regular distro root filesystem) and which code paths that enables. covers this in depth.

Anatomy of a snap

  • Format: a SquashFS image, mounted read-only under /snap/<name>/<revision> (or /var/lib/snapd/snap/... on some systems).
  • Metadata: meta/snap.yaml describes apps, services, plugs, slots, hooks. Parsing and representing this lives in the top-level snap package.
  • Components: optional separately-installable/removable pieces of a snap (e.g. optional kernel modules) with their own lifecycle tasks (mount-component, link-component, …) managed alongside the parent snap in overlord/snapstate.
  • Confinement declared by the snap: strict, classic, or devmode — see .
  • Identity & trust: snaps are tied to signed assertions () rather than being trusted by filename alone.

Classic systems vs. Ubuntu Core, at a glance

Both run the exact same overlord, the same managers, the same task kinds. The difference is almost entirely about which snaps exist (gadget/kernel/base present ⇒ Core-like behavior) and a few build/runtime checks (release.OnClassic, device-context, model assertion fields) that steer specific code paths. 2 Entry points & the multi-call binary

Every snapd binary you'll ever strace is really the same ELF file wearing a different hat.

In plain termsThere is essentially one Go program. It looks at the name it was started under (snapd vs snap vs an app name) to decide what to be, and it may first hop into a newer copy of itself shipped inside the snapd snap.

One binary, many names

The snap command and the snapd daemon share a single multi-call binary built from cmd/snapd. The real binary is installed as snapd (e.g. /usr/lib/snapd/snapd); /usr/bin/snap is a symlink pointing to it. At runtime the binary dispatches on argv[0]:

  • invoked as snapd → runs the daemon
  • invoked as snap (or any other name, as happens for snap application symlinks in /snap/bin) → runs the CLI

The sandbox helpers snap-confine and snap-exec are separate small binaries (compiled C and Go respectively, under cmd/snap-confine and cmd/snap-exec) that handle the actual execution pipeline described in — they are not part of the multi-call dispatch.

The snapd-tool-wrap trick for internal tools

Internal tools like snapd-apparmor, snap-preseed, and snap-gpio-helper are not standalone binaries either. A tiny C wrapper (snapd-tool-wrap, built from cmd/snapd-tool-wrap) is symlinked under each tool name in /usr/lib/snapd/. The wrapper sets argv[0]="snapd" and argv[1]=<tool-name>, then execv()s into the real snapd binary. The Go dispatch in cmd/snapd/main.go checks argv[1] for known tool names before falling through to the daemon. 

/usr/lib/snapd/snapd-apparmor -> argv[0] is set to "snapd-apparmor"
   -> exec("/usr/lib/snapd/snapd", ["snapd", "snapd-apparmor"])
      -> (inside cmd/snapd/main.go)
         -> argv[] == ["snapd", "snapd-apparmor"]
            -> run cmd/snapd/tool/snapd-apparmor.Main()

This keeps tool names from ever colliding with snap application names, since the only reserved argv[0] name is snapd (no snap can be named that).

Go deeper: the actual dispatch table in cmd/snapd/main.go

The real logic is a small switch argv0 at the top of cmd/snapd/main.go's main(). It keeps two package-level maps/slices that make the wiring explicit: 

// maps tool names (as passed in argv[1] by snapd-tool-wrap) to their Main()
var toolMains = map[string]func(){
    "snap-preseed":          snap_preseed.Main,
    "snapd-apparmor":        snapd_apparmor.Main,
    "snap-gpio-helper":      snap_gpio_helper.Main,
    "snap-recovery-chooser": snap_recovery_chooser.Main,
    "snap-fde-keymgr":       snap_fde_keymgr.Main,
}

// tools that expect to run from inside the re-exec'd snapd/core snap
var reexecTools = []string{"snapd-apparmor", "snap-gpio-helper"}

main() takes argv0 := filepath.Base(os.Args[0]) and switches on it: for case "snapd", it first checks whether os.Args[1] is a key in toolMains — if so it runs that tool's Main() and returns, otherwise it falls through to daemonMain() (cmd/snapd/daemon). For case "snap" (or anything else — i.e. any app symlink name under /snap/bin), it runs cliMain() (cmd/snapd/cli). daemonMain/cliMain are themselves package-level vars, not direct calls — a deliberate seam the tests use to mock them out.

Note the tool map here is a different (smaller) set of tools than the ones wired through snapd-tool-wrap above — e.g. snap-preseed and snap-fde-keymgr are reached this same way but via their own dedicated C wrapper symlinks, not necessarily all through the identical wrapper binary. reexecTools marks which of these tools are expected to actually be running from inside the re-exec'd snapd/core snap rather than the host-packaged copy.

Re-exec: always running the newest snapd

Both the daemon and the snap CLI support re-exec: on startup they compare their own version against the snapd or core snap installed on the system. If the snap is newer, execution restarts from the binary inside that snap — ensuring users always run the most up-to-date snapd without requiring a system package update. Because /usr/bin/snap is a symlink to the snapd binary and dispatch is based on argv[0], re-exec preserves the original argv[0], so the same CLI-vs-daemon dispatch applies in the new process.

Go deeper: how ExecInSnapdOrCoreSnap() decides, step by step

The logic lives in snapdtool/tool_linux.go, ExecInSnapdOrCoreSnap(), called early from both cmd/snapd/cli (CLI) and cmd/snapd/daemon (daemon) entry points:

  1. Resolve the currently-running executable's path via /proc/self/exe.
  2. Compatibility shim: if already running from inside the snap mount dir but an old (2.21-era) SNAP_REEXEC=0 is still set in the environment, unset it and return — this exists purely to stop a years-old workaround from permanently wedging re-exec off for a user's shell session.
  3. If re-exec is disabled (SNAP_REEXEC=0, the reExecKey constant), return and run as-is.
  4. If already running from inside /snap/... (i.e. this is the re-exec'd copy), return — no infinite loop.
  5. DistroSupportsReExec() gate: re-exec is skipped entirely unless release.OnClassic is true and the host distro is debian/ubuntu-like (release.DistroLike("debian","ubuntu")) — unless SNAP_REEXEC is explicitly set (not just default), which overrides the distro gate.
  6. Compute where the binary would live inside the snapd/core snap (pathInSnapdSnap); prefer /snap/snapd/current, fall back to /snap/core/current if the snapd snap isn't installed or doesn't ship that path.
  7. candidateVersionNewer() reads the candidate's info file and compares versions — re-exec only proceeds if the snap's copy is strictly newer, unless SNAP_REEXEC=force.
  8. Rewrite os.Args[0] cosmetically (so ps/top don't show a confusing path) unless the original was a bare symlink basename like /snap/bin/myapp, which must be preserved verbatim since later dispatch re-reads argv[0] to decide which app to run.
  9. syscall.Exec into the resolved path inside the snap, preserving the (possibly adjusted) argv — this is a real exec(2), not a subprocess spawn, so the PID is reused.
Why this matters for debugging: if you're stepping through snapd source but your changes don't seem to run, check whether you're actually executing the host package's binary or got re-exec'd into /snap/snapd/current — set SNAP_REEXEC=0 while developing against a host-installed build.

3 The execution pipeline

What happens, in order, between typing a command and your snap's code actually running.

In plain termsThree programs run in a strict chain, each exec-ing the next: snap run works out what to launch → snap-confine (the only privileged step) builds the sandbox → snap-exec, already inside the sandbox, starts the app. No snapd code remains once the app is running.
Everything above the dashed "SANDBOX" line runs with host privileges; everything below runs confined.

snap run

snap run reads the snap's metadata and prepares the command line to exec snap-confine. It resolves which revision is current, which app/hook/service is being invoked, environment variables (SNAP, SNAP_NAME, SNAP_REVISION, …), and whether this is a classic-confinement snap (which changes the arguments passed down significantly, since classic snaps mostly run unconfined on the host filesystem).

Go deeper: refresh-app-awareness — why a running app can block its own snap's refresh

Before snap run ever reaches snap-confine, it calls waitWhileInhibited() (cmd/snapd/cli/inhibit.go), which checks for a hint lock file for the snap (runinhibit.HintFile(snapName), managed by cmd/snaplock/runinhibit). This is the mechanism behind "refresh app awareness" — snapd can hold off refreshing a snap while it has running processes, and conversely a launch can block (with a user-facing notification) while a refresh that's already started finishes:

  1. If there's no hint file at all, the snap isn't inhibited — proceed immediately with a nil lock.
  2. If the hint file says refresh, snap run blocks (sending desktop notifications during the wait) until the refresh completes, then re-reads the (possibly now different) snap revision and app info before proceeding.
  3. If the hint says the snap is being removed or is disabled, the launch is refused outright (errInhibitedForRemove/errInhibitedForDisable) — there's nothing to wait for.
  4. Once clear, it returns a locked hint file lock that the caller must hold until the app is actually running inside its transient cgroup — releasing it earlier than that would let a refresh race in before snapd can detect the app is live via the cgroup it's about to be launched into.

snapRunApp() wraps all of this in a bounded retry loop (errSnapRefreshConflict, capped at one retry) for the narrow race where no hint file existed yet when the check ran, but a refresh started and created one immediately after — rather than crash or launch against a half-refreshed snap, it just re-checks once.

Only after all of this does runSnapConfine() (cmd/snapd/cli/cmd_run.go:1562) actually build the argv and exec into snap-confine — everything above runs as ordinary unconfined CLI code, talking to the daemon over /run/snapd.socket via the client package, before the sandbox boundary from the diagram above is ever crossed.

snap-confine: setting up the sandbox

snap-confine (C, cmd/snap-confine/snap-confine.c and friends) is the binary responsible for setting up the execution sandbox: preparing the mount namespace and activating sandbox profiles. It is installed with extra POSIX capabilities (not full root) and performs privileged setup work, then drops those capabilities before handing off.

  1. Parses its invocation (snap/component/app identity comes from SNAP_INSTANCE_NAME and friends in the environment, not just argv).
  2. Self-defense check: if AppArmor is supported on the system but snap-confine itself is running unconfined while effectively privileged, it refuses to continue — this blocks a classic privilege-escalation trick.
  3. Picks up the capabilities it needs in its effective set (CAP_SYS_ADMIN for mounts/unshare, CAP_SYS_CHROOT for pivot_root, CAP_DAC_OVERRIDE/CAP_DAC_READ_SEARCH, CAP_CHOWN, CAP_FOWNER, CAP_SYS_PTRACE, …) and marks a smaller subset as inheritable for helper child processes like snap-update-ns.
  4. Acquires a per-snap lock (sc_lock_snap) and a global lock, to serialize sandbox construction for the same snap.
  5. Builds the mount namespace: creates/reuses a persistent per-snap mount namespace (so repeated app launches are cheap), mounts the snap's SquashFS, sets up bind mounts for writable data areas, device cgroup/udev tagging, and applies any interface-granted extra mounts (mount backend, ).
  6. Applies the seccomp profile for the specific security tag being executed (sc_apply_seccomp_profile_for_security_tag).
  7. unshare(2)s into the new namespaces — this is the actual host/sandbox boundary crossing drawn in the diagram above.
  8. Finally relinquishes its capabilities and execs snap-exec inside the now-confined environment, with the AppArmor profile for the security tag already active.

Related helper binaries invoked along the way:

  • snap-update-ns (cmd/snap-update-ns) — applies incremental mount-namespace changes (used both at launch and when interface connections change while a snap is running).
  • snap-discard-ns (cmd/snap-discard-ns) — tears down a stale per-snap mount namespace, e.g. after a snap is refreshed.
  • snap-device-helper (cmd/snap-device-helper) — invoked by udev rules to add/remove device cgroup access as interfaces are connected/disconnected.
Go deeper: namespace reuse, locking, and the classic-confinement fork in the code

Not every launch rebuilds the sandbox from scratch. Repeated launches of the same snap are cheap because snap-confine persists and reuses a per-snap mount namespace. The real branch point in main() (snap-confine.c) is: 

if (!invocation.classic_confinement || sc_feature_enabled(SC_FEATURE_PARALLEL_INSTANCES)) {
    // strict (or classic+parallel-instances): full namespace/profile setup
    enter_non_classic_execution_environment(&invocation, &apparmor, real_uid, real_gid, saved_gid);
}
// classic confinement (without parallel instances): skips this entirely —
// no per-snap mount namespace, no freezer/cgroup setup, no snap-update-ns handoff

Inside enter_non_classic_execution_environment (snap-confine.c:813), namespace reuse is decided by sc_inspect_and_maybe_discard_stale_ns() (ns-support.c:586), which checks should_discard_current_ns() — true if any of:

  • the base snap's backing block device changed (base was refreshed)
  • homedirs configuration changed since the namespace was built
  • the managed CA-certificate DB generation on disk differs from what's baked into the preserved namespace

A separate 3-way outcome governs how hard to discard, computed by is_base_transition() (ns-support.c:548) comparing the base snap name recorded in $SC_NS_DIR/snap.<instance>.info against the current invocation: SC_DISCARD_NO (reuse as-is), SC_DISCARD_SHOULD (base revision changed, same base name — reusable, and importantly a stale-but-inhabited namespace is not force-killed: already-running processes keep using it while new launches get a fresh one), and SC_DISCARD_MUST (base name changed — must discard even with live processes in it).

If reusable, sc_join_preserved_ns() attaches to the existing namespace through a short-lived helper process communicating over a pipe pair (struct sc_mount_ns carries dir_fd — an O_PATH|O_DIRECTORY fd into the per-snap namespace-group control directory, plus pipe_helper/ pipe_master). If not, sc_bootstrap_mount_namespace() (mount-support.c:562) builds one from scratch: replicates the base rootfs (sc_replicate_base_rootfs), lays down the mount list, then sc_preserve_populated_mount_ns() snapshots it for future reuse and sc_store_ns_info() records the base name for next time's transition check.

All of this persistent state lives under SC_NS_DIR = "/run/snapd/ns" — one bind-mount file plus .info/.fstab metadata per snap instance. The locks from step 4 above (cmd/snaplock/lock.go) are separate flock files at dirs.SnapRunLockDir/<snap>.lock, unrelated to the namespace files themselves.

cgroup v1 quirk: the extra CAP_SETUID/CAP_SETGID capabilities snap-confine can be packaged with are only needed on cgroup v1 systems — joining/creating the freezer cgroup for a user namespace requires them there; cgroup v2's unified hierarchy doesn't.

snap-exec: last mile setup

snap-exec (Go, cmd/snap-exec) runs already inside the sandbox. It's responsible for the final setup before the actual target binary runs: resolving the app's command from snap.yaml, setting up the working directory, environment, and argv, then exec-ing the real entry point. By the time this process image is replaced, there is no more snapd-controlled code running — just the snap's own binary, confined.

4 Confinement & sandboxing mechanisms

What "sandboxed by default" is actually implemented with, and how an interface's policy becomes real kernel enforcement.

In plain termsInterfaces decide what a snap may do; security backends turn that into kernel-level artifacts (AppArmor profiles, seccomp filters, mount profiles, udev rules…). They are generated ahead of time by the daemon and merely loaded at launch, which keeps app start-up fast.

Confinement types

TypeMeaning
strictFull sandbox: dedicated mount namespace, AppArmor profile, seccomp filter, device cgroup. No access to anything outside the snap except what's explicitly granted via connected interfaces. The default and by far the most common.
classicRuns with (mostly) host filesystem visibility and without the strict AppArmor/seccomp sandbox — used for tools that fundamentally need broad host access (e.g. editors, some SDKs). Still goes through snap-confine, but that stage sets up a much lighter environment. Publishing a classic-confinement snap to the store requires manual review.
devmodeDeveloper/debug mode: policy is still generated and loaded, but AppArmor/seccomp denials are logged instead of enforced (complain mode). Used while developing a snap's interface usage; devmode snaps cannot be released to the stable store channel.

Go deeper: AppArmor template assembly, the system-key cache, and seccomp's two-stage compile

AppArmor profile assembly (interfaces/apparmor/backend.go): a profile is built from a base template string containing ###PLACEHOLDER###-style tokens, matched by templatePattern = regexp.MustCompile("(###[A-Z_]+###)"). deriveContent()/addContent() replace each placeholder with the interface-contributed snippet text collected for that security tag from the Specification; joinRules() concatenates multiple interfaces' snippets for the same tag before substitution. The separate snap-update-ns helper gets its own profile built the same way via addUpdateNSProfile() against a distinct template, since it's a privileged helper in its own right.

The system-key cache (interfaces/system_key.go): regenerating every security profile on every snap run would be far too slow, so snapd caches a small JSON systemKey struct and compares it against the one recorded alongside the last-generated profiles — not a hash of profile content, but a fingerprint of everything that could make previously-generated profiles stale: Version (an escape hatch — bump to force invalidation on format changes), BuildID (snapd's own build-id, so upgrading the snapd binary alone invalidates the cache), AppArmor feature/parser versions, NFSHome, OverlayRoot, seccomp actions/compiler version, cgroup version. A mismatch means snap run must wait for (or trigger) regeneration before it's safe to proceed; the code distinguishes "can't even compare" (ErrSystemKeyVersion) from "no cache yet" (ErrSystemKeyMissing).

Seccomp is compiled in two stages, and not by snap-confine (interfaces/seccomp/backend.go, cmd/snap-seccomp): the Go-side Specification is written as a textual .src profile; a dedicated internal binary, snap-seccomp compile <in> <out>, uses libseccomp-golang (a cgo binding) to compile it ahead-of-time into a native seccomp-BPF program on disk (a .bin2 file — the suffix bumped from an older .bin format). parallelCompile() compiles multiple changed profiles concurrently across worker goroutines. At actual launch time snap-confine only loads the pre-compiled .bin2 — all compilation happens off the hot launch path, and SeccompCompilerVersion is itself a system-key input, so upgrading the libseccomp toolchain alone forces regeneration.

Compatibility gate: using the non-enforcing, log-only SECCOMP_RET_LOG action (what devmode relies on) requires kernel support and libseccomp support and libseccomp-golang binding support to all agree — any one missing falls back silently rather than erroring.

Mount namespaces & incremental updates

Each snap gets its own persistent mount namespace (reused across app launches for speed). When interface connections change while a snap might already be running (e.g. a live interface connect/disconnect), snapd doesn't tear down and rebuild the whole namespace — it computes a diff and applies it incrementally via snap-update-ns, using a small per-snap "mount profile" description (interfaces/mount) rather than re-running all of snap-confine.

Go deeper: the actual diff algorithm in snap-update-ns

The desired state is written by mount.Backend as one fstab-syntax file per snap at dirs.SnapMountPolicyDir/snap.<name>.fstab (bind mounts only). When it changes, UpdateSnapNamespace() (interfaces/mount/ns.go) execs snap-update-ns for that snap, which loads current state (what's actually mounted) and desired state, both as osutil.MountProfile, and computes the difference in neededChanges(current, desired) (cmd/snap-update-ns/change.go:561):

  1. Paths are cleaned/sorted; a desiredMap is built keyed by mount-point directory.
  2. Each entry carries an XSnapdEntryID tag used purely for change-tracking (not a real mount option). An entry present in both current and desired with identical directory and options is reused as-is and left mounted.
  3. Entries whose options changed, or that are no longer desired, are unmounted — even though from the kernel's point of view the directory briefly looks "mounted throughout," the diff still tears down and remounts it if anything differs.
  4. Synthetic auto-created helper mounts (XSnapdSynthetic) are kept only if the non-synthetic entry that needed them (XSnapdNeededBy) is still in the desired set — otherwise they're torn down too, even though nothing directly asked for their removal.
  5. DoPerform() executes the resulting minimal ordered list of mount/unmount syscalls.

mount.Backend.updateOrDiscard() picks between this incremental update and a full discard (handing off to the separate, much simpler snap-discard-ns C binary, which doesn't diff — it just tears the persisted namespace files down entirely) depending on whether the change is incremental or a base-snap transition that demands a full rebuild ().

Device access: cgroups + udev

Hardware access (e.g. a serial-port or raw-usb interface) is mediated through the device cgroup. udev rules generated by the udev backend tag matching devices; when a tagged device event fires, snap-device-helper is invoked to add/remove that device from the snap's cgroup device list, keeping kernel-level device access in sync with live interface state without needing to restart the snap's processes.

Go deeper: the generated udev rule shape, and cgroup v1 vs v2

Each matching interface contributes a two-rule pattern (interfaces/udev/spec.go):

# <interface-name>
<device-match-snippet>, TAG+="<tag>"
TAG=="<tag>", SUBSYSTEM!="module", SUBSYSTEM!="subsystem", \
  RUN+="<helper-dir>/snap-device-helper $env{ACTION} <tag-arg> $devpath $major:$minor"

The first rule tags matching devices; the second fires snap-device-helper with the udev action (add/change/remove), tag, devpath, and major:minor whenever a tagged device event occurs. The SUBSYSTEM!= filters exclude kernel-module and sysfs-subsystem-class pseudo-devices, which aren't real device nodes.

On add/change, the helper calls sc_device_cgroup_new() then sc_device_cgroup_allow() (grants access); on remove, sc_device_cgroup_deny() (revokes) — any other action is a no-op. sandbox/cgroup.IsUnified() is the single detection point for cgroup v1 vs v2 (memoized), and device-cgroup-support.h's sc_device_cgroup_* functions abstract the version difference away from the helper itself. These grants are live — no snap-process restart needed, which is what lets a newly plugged USB device become accessible to an already-running confined process immediately.

5 Overlord & the ensure loop

How the running snapd daemon organizes its own work — the part of snapd that never touches a sandbox.

In plain termsThe daemon is a loop. At least every five minutes — or immediately when something calls for it — it asks every manager "is there anything you need to do?". Managers answer by creating work items (tasks), and a task runner executes them.

overlord.Overlord

snapd's own execution is orchestrated by overlord.Overlord (overlord/overlord.go) and the state managers underneath it. Managers are initialized and driven via the overlord.StateManager interface. Execution comprises:

  1. A start-up phase: StateStarterUp.StartUp is called on every manager that implements it.
  2. The ensure loop runs repeatedly: at minimum every 5 minutes, but immediately whenever there's pending work.
  3. Each loop iteration calls StateManager.Ensure on every manager, in a fixed wiring order.
  4. On shutdown, StateManager.Stop is called on every manager.

Optional lifecycle interfaces a manager may also implement: StateStarterUp, StateWaiter, StateShutDowner, and StateStopper — see overlord/stateengine.go for their exact contracts and invocation order.

Go deeper: loadState() — the file lock, boot-id check, and one-shot migrations

Overlord.loadState() (overlord/overlord.go:308) is what actually runs before any manager is constructed:

  1. Opens and locks a dedicated lock file (initStateFileLock() / lockWithTimeout(o.stateFLock, stateLockTimeout), timeout 1 minute) — this is an OS-level flock, separate from the in-process state.State mutex, and exists so two snapd processes can never both think they own the state file.
  2. Reads the current boot id (osutil.BootID()) — used later by initRestart to detect "did the system actually reboot since I last ran," which is how pending-restart tracking distinguishes a real reboot from a plain daemon restart.
  3. Fresh system: if /var/lib/snapd/state.json doesn't exist yet, it fails fast if the containing directory is missing (a packaging invariant), otherwise constructs a brand-new state.New(backend) and calls patch.Init(s) to stamp it as already being at the latest patch level — a new system never needs migrations.
  4. Existing system: state.ReadState(backend, r) deserializes the JSON file, then patch.Apply(s) runs any outstanding one-shot state migrations — the overlord/patch package versions the on-disk state schema itself, independent of the snapd binary version, so upgrading across several snapd releases at once still walks through every intermediate migration in order.

Only after loadState() returns does New() go on to construct every manager in a fixed order (hook, restart, snap, service, assert, iface, device, …) via repeated o.addManager(mgr) calls, each of which registers the manager both for the StateManager lifecycle and, where relevant, its task handlers with the shared state.TaskRunner.

What Ensure() is actually for

A manager's Ensure method implements a small state machine: first check whether any transition requiring a system change is needed, then, if so, set that change up (by creating a state.Change full of tasks — ). The regular "poll the store for updates" logic and automatic refresh scheduling are implemented exactly this way inside overlord/snapstate.

state.TaskRunner — the engine that actually executes task do/undo handlers — is wired into the ensure loop as if it were a manager itself, and its Ensure runs last in each loop iteration, after every manager has had a chance to enqueue new work.

Code anywhere in snapd can call state.State.EnsureBefore(d) to make the ensure loop run again sooner than its normal schedule — this is how, e.g., finishing one task can immediately trigger progress on dependent tasks instead of waiting up to 5 minutes.

Go deeper: the actual loop() body and pruning

The real loop (overlord/overlord.go, func (o *Overlord) loop()), simplified:

for {
    o.ensureTimerReset()
    err := o.stateEng.Ensure()      // calls every manager's Ensure(), TaskRunner last
    o.ensureDidRun()
    select {
    case <-o.loopTomb.Dying():
        return nil
    case <-o.ensureTimer.C:         // normal 5-minute tick, or an EnsureBefore()-shortened one
    case <-pruneTicker.C:            // every 10 minutes
        st.Lock()
        st.Prune(o.startOfOperationTime, pruneWait, abortWait, pruneMaxChanges)
        st.Unlock()
    }
}

Constants (overlord/overlord.go top-level vars): ensureInterval = 5 * time.Minute, pruneInterval = 10 * time.Minute, pruneWait = 24 * time.Hour (how long a ready Change is kept before being eligible for pruning), abortWait = 24 * time.Hour * 3 (how long a stuck, not-ready Change is left alone before being force-aborted), pruneMaxChanges = 500 (a hard cap — even recent Changes get pruned once there are too many, oldest-ready first).

EnsureBefore(d) doesn't just reset a timer blindly — it compares the requested time against the currently-scheduled ensureNext and only moves it earlier, never later; if the requested time has already passed, it schedules immediately. This is what lets dozens of independent call sites across every manager call EnsureBefore(0) without fighting each other over the schedule.

Preseeding quirk: in preseed mode (building a snap image ahead of first boot), an Ensure() error causes the loop to acquire the state lock (deliberately with no deferred unlock, to avoid a race on process exit) and terminate the whole preseeding process immediately — a half-seeded preseeded image is treated as worse than a hard failure.
Simplified: every registered manager's Ensure() runs each loop iteration; TaskRunner's runs last so freshly-created tasks get picked up without waiting for the next tick.

6 State, Changes & Tasks

The persistence and execution model that lets any snapd operation survive a reboot mid-flight.

In plain termsAll of snapd's memory lives in one JSON file guarded by one lock. Every operation is a Change: a graph of Tasks, each with a do and an undo handler. Because this is saved to disk constantly, an interrupted install simply resumes (or rolls back) after a restart.

state.State & the global lock

Working persistent state is implemented by overlord/state.State, governed by a single global lock (State.Lock/Unlock). Mutations made while holding the lock are atomically flushed to disk when the lock is released. This one file (/var/lib/snapd/state.json) is why snapd survives its own restarts, reboots, and power loss mid-operation without losing track of what it was doing.

Rule: release the lock only around genuinely slow external operations — network calls, large copy/compress/decompress of on-disk data. Re-validate any mutable state you read before the unlock once you reacquire the lock; never blindly overwrite with values read before the gap.
Go deeper: what Unlock() actually does — synchronous checkpoint with retries

State.Unlock() (overlord/state/state.go:294) is not just a mutex release. If nothing was modified since Lock() (tracked by an internal modified flag set by any writing()-guarded call — the same guard that panics with "internal error: accessing state without lock" if state is touched without the lock held), it just unlocks. Otherwise:

  1. Serializes the entire state to JSON (checkpointData() → json.Marshal(s)).
  2. Calls s.backend.Checkpoint(data), which writes it to disk.
  3. If that write fails, it retries for up to 5 minutes (unlockCheckpointRetryMaxTime), sleeping unlockCheckpointRetryInterval = 3s between attempts — Unlock() genuinely does not return until the checkpoint succeeds or this budget is exhausted.
  4. If still failing after 5 minutes, it panics — deliberately: proceeding with in-memory state that can't be persisted would mean losing track of in-flight operations on the next crash/restart, which is worse than crashing now.

This is also why handler code that releases the lock around a slow operation and re-acquires it ('s locking rule) has real cost on both ends — every unlock with pending modifications is a synchronous disk write, not a cheap in-memory operation.

state.Change and state.Task

Any system change is realized as a dependency graph of tasks: a state.Change containing state.Task nodes connected by "waits for" edges. Both are identified by a kind — an explanatory string. Both are persisted, so operations survive restarts. Higher-level code composes the right tasks into a state.TaskSet (helpers like snapstate.InstallWithGoal or ifacestate.Connect return one), which then gets wrapped into a state.Change ready for execution.

A few real task kinds, to make this concrete (there are many more — these are grouped by the manager that owns them):

download-snapmount-snapcopy-snap-datalink-snap unlink-snapstart-snap-servicesrun-hooksetup-profiles auto-connectvalidate-snapcreate-recovery-systemrequest-serial

state.TaskRunner & task statuses

TaskRunner executes Change/Task do/undo logic. Each task kind's handlers are registered with TaskRunner.AddHandler by the owning manager. A task moves through statuses: DoStatus → DoingStatus → (success) DoneStatus, or on failure UndoStatus → UndoingStatus → UndoneStatus, with ErrorStatus/HoldStatus as other terminal outcomes.

If a task errors, the runner normally undoes the completed tasks it depended on — not the failing task itself. Each handler is expected to clean up its own partial effects on its own error paths. Independent Changes, and independent Tasks within one Change, normally execute concurrently.

Idempotency matters: because snapd can restart mid-task, do/undo handler logic may re-run from the top. On-disk/external changes must be idempotent or equivalent to re-apply; working-state changes must either be idempotent too, or be atomically combined with the task's next SetStatus call before returning — otherwise there's a window where a restart replays a handler that doesn't expect its own already-committed side effects.
Go deeper: TaskRunner.run() — one goroutine per task, locks acquired in a fixed order

Each due task gets its own goroutine (overlord/state/taskrunner.go, func (r *TaskRunner) run(t *Task)), tracked via a *tomb.Tomb keyed by task ID in r.tombs. The handler itself runs with no state lock held — it's the handler's own job to lock/unlock as needed (). When the handler returns, the goroutine reacquires control and does its bookkeeping: 

tomb.Kill(handler(t, tomb))   // run the actual do/undo handler
// Locks must be acquired in the same order everywhere:
r.mu.Lock(); defer r.mu.Unlock()
r.state.Lock(); defer r.state.Unlock()
delete(r.tombs, t.ID())
// ... inspect tomb.Err() and transition the task's status

That comment — "locks must be acquired in the same order everywhere" — is load-bearing: r.mu (the TaskRunner's own internal mutex) is always taken before r.state's lock, in every code path, specifically to avoid a lock-ordering deadlock between the runner and concurrent state access elsewhere.

On success the result is one of four real outcomes, switched on the error type returned by the handler:

  • nil error: status advances normally — DoingStatus→DoneStatus (then t.HaltTasks(), its dependents, are queued) or UndoingStatus→UndoneStatus (then t.WaitTasks(), what was waiting on it, proceeds).
  • *Retry: the handler wants to be called again later — if a delay (After) was given, the task is rescheduled via t.At(...) rather than run again immediately.
  • *Wait: the task parks in WaitStatus until something external resolves it (used e.g. for restart-pending handoffs).
  • any other error: r.abortLanes(t.Change(), t.Lanes()) is called first (see Lanes below), then this task's own status is set to ErrorStatus — note the failing task itself does not get undone by this mechanism; only tasks it depended on do, per the runner's general contract.

If the runner is in the middle of Stop() (shutting down) and a handler returns an unexpected error, it's reinterpreted as a *Retry rather than a real failure — errors during shutdown are assumed to be cancellation artifacts, not genuine task failures, so they shouldn't poison the Change's state.

Lanes: independent failure domains

By default, any task failing aborts the entire Change. Lanes let you partition tasks within one Change into independent failure domains — e.g. auto-refreshing 10 snaps in a single Change, one lane per snap, so one snap's refresh failing doesn't roll back the other nine. Assign with Task.JoinLane(n) where n comes from State.NewLane(); unassigned tasks are implicitly lane 0. A task can belong to multiple lanes and survives if any of its lanes stays healthy.

Go deeper: how AbortLanes actually decides what to kill

Change.AbortLanes(lanes []int) (overlord/state/change.go:690) delegates to an internal abortLanes that walks every task in the Change: a task in any of the failed lanes gets aborted unless it also belongs to at least one lane not in the failed set — that's the literal mechanism behind "a task survives if any of its other lanes is healthy." Aborted tasks transition based on current status (matching the task-level rules from the checklist): not-yet-started tasks are held and never run, in-progress tasks are signaled via their tomb (tb.Kill(nil) in TaskRunner.abortLanes) and later undone, completed tasks are queued for undo.

There's also Change.AbortUnreadyLanes() — a related but distinct operation that computes, from scratch, which lanes currently have any not-yet-ready task in them, and aborts exactly those lanes. This is what a user-initiated snap abort <change-id> effectively uses: abort whatever's still in flight, lane by lane, rather than needing the caller to already know which lanes are "the failing ones."

Conflicts & AddBlocked preconditions

Lanes handle failure isolation within one Change. A different problem: stopping two different Changes from operating on the same snap concurrently (e.g. connecting an interface on a snap that's mid-removal). Before creating a new Change touching a snap, snapd checks for already in-progress operations on it and returns a conflict error rather than starting — central logic in overlord/snapstate/conflict.go.

Some task families need a coarser rule than conflicts can express cleanly — e.g. at most one hook task running at a time per snap, or interface tasks that touch more than one snap. These register precondition predicates via TaskRunner.AddBlocked: before running a candidate task, every predicate sees the candidate and the set of currently-running tasks, and can defer it.

Go deeper: how a task declares which snaps it affects — and a live example of the "re-validate after reacquiring the lock" rule

Conflict-checking needs to know which snap(s) an arbitrary task touches. Most snapstate tasks carry a snap-setup entry, so SnapsAffectedByTask() (overlord/snapstate/conflict.go) reads that directly. But tasks from other managers (interfaces, hooks, …) don't carry snap-setup data, so this is exactly the kind of cross-manager need CODING.md's hook-registration pattern exists for: 

var affectedSnapsByKind = make(map[string]AffectedSnapsFunc)  // keyed by task kind
var affectedSnapsByAttr = make(map[string]AffectedSnapsFunc)  // keyed by "has this task attribute"

func AddAffectedSnapsByKind(kind string, f AffectedSnapsFunc) { affectedSnapsByKind[kind] = f }
func AddAffectedSnapsByAttr(attr string, f AffectedSnapsFunc) { affectedSnapsByAttr[attr] = f }

Other managers' init()/constructor code registers into these maps — the same "break the cycle with a registration mechanism" pattern as snapstate.ValidateRefreshes () — so snapstate never has to import ifacestate or hookstate just to know what a task of theirs touches.

A concrete instance of the "re-validate after the lock gap" rule from : checkChangeConflictIgnoringOneChange() optionally takes the caller's in-memory *SnapState and compares it, via reflect.DeepEqual, against what's actually in the state right now. The doc comment explains why: callers sometimes have to unlock the state to talk to the store (fetching snap info for install, or what-needs-refreshing for refresh) — and a conflicting Change could "sneak in" during that window, before the caller's TaskSet is even created. If the comparison fails, it returns a ChangeConflictError rather than silently proceeding on stale data — this is the exact failure mode the checklist item about re-validating mutable state is there to prevent.

Cleanup handlers

TaskRunner.AddCleanup registers logic that runs only after the entire Change is ready — i.e. outside conflict protection. Use it only for task-local temporary data; by the time it runs it must not touch state that could interfere with other Changes or the system generally.

7 Interfaces: plugs, slots & policy

How "a snap may use the camera" becomes an enforced, auditable, revocable grant.

In plain termsA plug is a snap asking for something; a slot is something offering it; a connection joins them and is what actually grants access. Built-in rules in snapd plus per-snap rules signed by the store decide whether a connection is allowed, and whether it happens automatically.

Plugs, slots, connections

  • A slot offers access to a resource (e.g. network, camera, a content share). Often provided implicitly by the system snap, sometimes by an app/gadget snap.
  • A plug is a snap's request to use a given interface's slot.
  • A connection links a specific plug to a specific slot. Only once connected does the corresponding security-backend policy () actually get granted.
  • Each built-in interface (there are 228+ files under interfaces/builtin) encapsulates: static metadata, declaration policy defaults, auto-connect behavior, and contributions to each relevant security backend's Specification.

interfaces.Repository & building an interface

interfaces.Repository (interfaces/repo.go) is the in-memory abstraction tracking every snap's plugs/slots and connections, and orchestrating backend Specification generation. Every built-in interface implementation satisfies interfaces.Interface (interfaces/core.go), minimally Name() and AutoConnect(), and registers itself with registerIface from an init() in interfaces/builtin/all.go.

  • Use commonInterface (interfaces/builtin/common.go) when the interface is purely data-driven static metadata + security snippets — interfaces/builtin/alsa.go is a clean example.
  • Write a dedicated type when custom validation, connection behavior, or backend logic is needed — interfaces/builtin/empty.go is a compact example of the available extension points.
  • Nearby interfaces with similar resource shape are usually the best reference to copy from.
Go deeper: Repository's internal indexes and how backend regeneration actually iterates

Repository (interfaces/repo.go) is guarded by one sync.Mutex for the whole struct — no fine-grained locking. Its indexes:

  • plugs map[naming.InstanceName]map[string]*snap.PlugInfo and slots likewise — keyed [snapInstance][plugOrSlotName].
  • slotPlugs map[*snap.SlotInfo]map[*snap.PlugInfo]*Connection and the inverse plugSlots — connections are indexed by pointer identity of the PlugInfo/SlotInfo structs, kept in sync in both directions.
  • appSets map[naming.InstanceName]*SnapAppSet — tracks which snaps (+ components) are registered at all.
  • conflictingConnectedInterfaces map[string]map[string]bool — opt-in pairs of interfaces that must never both be connected simultaneously on the same snap.

Registration (AddAppSet) validates the snap info and refuses double-registration, but a plug/slot whose declared Interface name isn't a known interface is silently skipped rather than erroring — by design, so an older snapd doesn't fail to install a snap that merely declares a plug/slot kind it doesn't yet understand.

Backend regeneration (SnapSpecification) works on one backend, one snap per call — it is not "regenerate everything for everyone." The caller (ifacestate's setup-profiles handler) loops over the affected backends × affected snaps itself. For one call: creates a fresh Specification for that backend, then for every slot the snap owns calls AddPermanentSlot once and AddConnectedSlot once per live connection on it; symmetric for plugs.

Known wart: if AddConnectedPlug/AddConnectedSlot fails permanently for a connection (e.g. generated policy can't load on this kernel), the broken connection stays in the in-memory Repository and every future regeneration attempt retries and fails again — only a snapd restart clears it, since the connection was never persisted in the first place.

InterfaceManager / ifacestate

overlord/ifacestate.InterfaceManager keeps every snap's security profiles up to date using the interfaces package, and persists which connections exist (ifacestate.ConnectionState). Paradigmatic task kinds: setup-profiles, auto-connect, connect.

Hotplug (overlord/ifacestate/hotplug.go) handles devices that appear/disappear at runtime (USB, etc.), creating/removing slots and reconnecting as appropriate without a reboot.

Go deeper: the auto-connect candidate algorithm, interface hooks, and the hotplug device key

doAutoConnect (the auto-connect task handler), step by step:

  1. Resolves a task-aware DeviceContext and finishes any pending restart first — guards against stale interface data if the preceding link-snap itself triggered a restart (e.g. installing a new core/base snap).
  2. Gadget-declared connections first: connections listed under connections: in gadget.yaml are added before any generic auto-connect logic runs, tagged ByGadget: true.
  3. Content-provider wait: for each plug using the content interface, computes its default providers; if any default provider is itself being installed in another not-yet-finished Change, returns &state.Retry{} so auto-connect reruns once that provider is actually ready — this is what stops a snap from racing its own content-sharing dependency.
  4. For each candidate plug/slot pair found via the Repository, runs the real policy gate (next card) plus an opt-in config check (filterAllowedAutoConnectionSlots) that lets a slot-providing snap opt a specific connection out via its own snap set configuration.
  5. Guards against racing another in-flight Change touching the same snap pair before committing.

Interface hooks (overlord/ifacestate/hooks.go) follow a fixed naming scheme: prepare-plug-<iface>, prepare-slot-<iface>, connect-plug-<iface>, connect-slot-<iface>, and the unprepare-*/disconnect-* equivalents. These run as ordinary run-hook tasks spliced into the connect/disconnect task chain — prepare-* hooks run before the connection is established and can abort it; connect-* hooks run after, letting each side's snap validate or react to the new grant.

Hotplug device key (overlord/ifacestate/hotplug.go): the stable identifier used to recognize "the same physical device" across reconnects and reboots is a SHA-256 over udev attributes grouped into four buckets — Name, Vendor, Model, Identifier (first non-empty attribute per bucket). An interface can supply its own HotplugKey(device) via a HotplugKeyHandler interface; otherwise the default needs at least 2 of the 4 buckets populated, or it returns an empty key meaning "this device can't be keyed reliably" (and hotplug support is skipped for it).

Declaration policy: who gets to connect what

Plug/slot rules live in two layers, evaluated with a strict precedence order (topmost wins, evaluation stops at first match):

  1. deny-* in the plug's snap-declaration (store-published, per-snap)
  2. allow-* in the plug's snap-declaration
  3. deny-* in the slot's snap-declaration
  4. allow-* in the slot's snap-declaration
  5. deny-* in the plug's base declaration (hardcoded in snapd source, commonInterface.baseDeclarationPlugs)
  6. allow-* in the plug's base declaration
  7. deny-* in the slot's base declaration
  8. allow-* in the slot's base declaration

In short: store rules beat hardcoded rules, plug rules beat slot rules, deny beats allow within the same stanza.

Three keys cover the lifecycle:

  • allow/deny-installation — can the snap even declare this plug/slot? An interface whose base declaration denies plug installation by default is super-privileged — unusable without a store snap-declaration explicitly overriding it (e.g. snapd-control).
  • allow/deny-connection — can a manual snap connect succeed? Commonly used to require attribute compatibility (the content interface requires matching content attribute values on both sides).
  • allow/deny-auto-connection — is this plug/slot pair wired up automatically on install, with no user action? Ignores allow-connection entirely, and only fires when there is exactly one candidate slot for a plug (the "greedy"/arity rule, governed by slots-per-plug / plugs-per-slot, default 1 and * respectively).
Authoritative source: full rule-constraint semantics (maps=AND, lists=OR, $SLOT()/$PLUG()/$MISSING special forms, on-store/on-classic device-context constraints) live in interfaces/builtin/README.md and in code in asserts/ifacedecls.go. Keep policy reasoning there — don't re-derive it from scratch per-interface.
Go deeper: how the 8-step precedence is literally encoded in Go

The compiled rule types live in asserts/ifacedecls.go — PlugRule/SlotRule each hold AllowInstallation/DenyInstallation/AllowConnection/DenyConnection/AllowAutoConnection/DenyAutoConnection []*...Constraints — note the slice: each key can carry several alternative constraint sets, which is the list-of-maps = OR semantics from the README. The actual precedence evaluator is a separate package, interfaces/policy/policy.go, not ifacedecls.go itself. Its ConnectCandidate.check(kind) encodes the 8-step order as literal early returns — and it's a stronger statement than "store beats base": 

if plugSnapDeclaration has a PlugRule for this interface:
    return checkPlugRule(..., snapRule=true)   // and STOP — no fallthrough even on deny
else if slotSnapDeclaration has a SlotRule:
    return checkSlotRule(..., snapRule=true)
else if baseDeclaration has a PlugRule:
    return checkPlugRule(..., snapRule=false)
else if baseDeclaration has a SlotRule:
    return checkSlotRule(..., snapRule=false)
else:
    return nil, nil   // no rule at all for this interface

The existence of a plug-side snap-declaration rule for this interface short-circuits everything else — it is not merged with slot-side or base-declaration rules at all, even partially.

Within one matched rule, checkPlugRule/checkSlotRule first try every alternative in the Deny* list; if any alternative matches, the connection is denied immediately. Only if none of the deny alternatives match does it try the Allow* list — if none of those match either, it's denied by omission; if one matches, its resolved SideArity (the slots-per-plug/ plugs-per-slot values) is returned for the arity/greedy-match rule to use.

The $SLOT()/$PLUG()/publisher-id special forms are implemented as a small compiled expression tree (attrMatcher, built by compileAttrMatcher) evaluated against an AttrMatchContext — ConnectCandidate itself implements that context via PlugAttr/SlotAttr/PlugPublisherID/SlotPublisherID methods, so the matcher never needs to know where the attribute values actually come from.

Reading the code: the deny-check helper's "matched" convention is inverted from what you'd expect — it returns err == nil to mean "this alternative matched, therefore deny," not "the check itself failed." Worth remembering before you go looking for a boolean return.

Adding a new built-in interface, in short

  1. Find the nearest existing interface with a similar resource shape under interfaces/builtin and start from its structure.
  2. Decide the base-declaration pattern from interfaces/builtin/README.md's policy-pattern catalog (auto-connected implicit slot? manually-connected app-provided slot? super-privileged?) — this determines default allow/deny-* values.
  3. Implement whichever backend-contribution methods are actually needed (AppArmor snippet, seccomp syscalls, udev tagging, …) — only the ones relevant to the resource.
  4. Add sanitizers if the plug/slot carries attributes that need validating/normalizing (see interfaces/core.go).
  5. Register in interfaces/builtin/all.go and write tests beside the implementation, using interfaces/ifacetest fixtures; cover static info, sanitizers, auto-connect decisions, and generated snippets.

8 The daemon & REST API

How "do something" requests get from the snap CLI (or anything else) into the overlord.

In plain termsEverything talks to snapd through a REST API on a local unix socket. Quick reads answer directly; real work returns a Change id immediately and runs in the background, which clients poll. Snaps themselves use snapctl, which goes through a separate, more restricted socket.

HTTP over a unix socket

snapd provides an HTTP API over the /run/snapd.socket unix socket — this is how most of the snap command's own operations are requested. It's implemented in the daemon package (one api_*.go file per API area — apps, asserts, find, download, interfaces/connections, confdb, debug, quotas, validation-sets, …). Handlers mostly call into overlord state-manager helpers rather than doing work themselves.

Go deeper: the Command struct, how a request is authorized, and the two sockets

Every route is a daemon.Command (daemon/daemon.go): Path/PathPrefix, a GET/PUT/POST handler func each, and — critically — a separate ReadAccess/WriteAccess pair, each an accessChecker. Concrete checkers: openAccess{} (anyone), authenticatedAccess{Polkit}, rootAccess{}, snapAccess{} (only from inside a confined snap), and the interface*Access family gated on a connected interface.

Command.ServeHTTP resolves access roughly as:

  1. Pulls ucred (peer uid, originating socket path) out of the request context — stashed earlier by a custom net.Conn wrapper that reads SO_PEERCRED once at Accept() time, not per-request.
  2. Picks ReadAccess for GET or WriteAccess for PUT/POST and calls its CheckAccess.
  3. Checks, in order: does the request come from an allowed socket at all → is the access level open → is there an authenticated macaroon user → is ucred.Uid == 0 (root bypasses everything) → does a PolkitAction authorize it (checked last, specifically to avoid an interactive auth prompt when an earlier, non-interactive check would already have allowed it) → otherwise deny.

Two distinct sockets, different defaults: /run/snapd.socket (the main API) vs. /run/snapd-snap.socket (the snapctl-only socket). rootAccess/authenticatedAccess only allow the main socket; snapAccess{} allows only the snapctl socket. The interface*Access checkers allow both, but on the snapctl socket additionally resolve the calling snap's instance name from ucred and require an active interface connection matching one of the endpoint's required interfaces — this is the real mechanism behind interface-gated endpoints (e.g. requiring snapd-control) being reachable from inside a confined snap. On the main socket, interface checks are skipped entirely — root-on-the-main-socket is trusted more than any interface grant.

How the Change id becomes a URL: for a 201/202 response, the handler puts "resource": "/v2/changes/<id>" into the result map; the generic response writer reads that and sets it as the HTTP Location header. There's no server-side long-poll — the snap CLI just issues repeated GET /v2/changes/{id} calls to watch progress (see the next card).

The async-change response pattern

For anything that does real work, a handler builds a state.TaskSet via a manager helper (ifacestate.Connect for connecting an interface, snapstate.InstallWithGoal for installing, etc.), wraps it in a state.Change, and returns an async response: HTTP 202 Accepted with a Change id. The caller then polls GET /v2/changes/{id} to watch progress/completion — this is exactly why snap install on the CLI shows a progress bar rather than blocking the HTTP call itself.

snapctl: snaps talking back to snapd

A snap (typically from inside a hook) calls back into snapd via snapctl, which internally hits the /v2/snapctl endpoint over a different socket, /run/snapd-snap.socket. The command itself is a thin forwarder: it ships parameters to the endpoint and relays output/exit code back. The real subcommand logic (set, get, services, is-connected, …) lives in overlord/hookstate/ctlcmd.

Go deeper: the subcommand registry, and why a slow snapctl call blocks the whole daemon

overlord/hookstate/ctlcmd/ctlcmd.go keeps a global registry, commands = make(map[string]*commandInfo, 32). Each subcommand file (set.go, get.go, services.go, …) calls addCommand(name, shortHelp, longHelp, generatorFunc) from its own init() — every subcommand is a self-registering plugin into this one map, the same pattern as the interface-hook naming scheme in . A subcommand struct embeds baseCommand to get the common plumbing (name/uid/stdout/stderr/context/change-id) for free and only implements its own flags and Execute(args []string) error.

The daemon's /v2/snapctl handler constructs a hookstate.Context tied to the hook's already-running *state.Task (or, for snapctl calls not tied to any hook — e.g. triggered from a running service — an ephemeral context with no backing task). It looks up the subcommand name in commands, instantiates it via the registered generator, and calls Execute.

Crucial detail: Context.Lock() acquires the context's own per-instance mutex and then the real, global state.State lock — the exact same lock the task runner and every other handler use, not a separate snapctl-only lock. That means a snapctl call made from inside a hook genuinely blocks on and contends with the rest of the daemon's state access, and conversely a slow snapctl call blocks everything else waiting on the state lock. This is precisely why hook/snapctl operations are expected to be fast — there's no isolation between them and the main state machine.

Manager-package import rules apply to the package roots themselves, not recursively to every file beneath a directory:

  • overlord/snapstate is imported by peer managers and must not import their package roots back. It defines fundamental shared types (e.g. DeviceContext) that nearly everything else depends on.
  • overlord/assertstate and overlord/hookstate should likewise be mostly consumed, not consumers of peer managers.
  • overlord/devicestate sits at the opposite end — it uses most other managers, since device/boot orchestration legitimately needs to reach into snap, assertion, and interface state.
  • Subpackages like overlord/ifacestate/ifacerepo, overlord/snapstate/backend, or overlord/configstate/config are distinct package boundaries — importable when the dependency direction is sound and there's local precedent.

When a cycle is otherwise unavoidable, break it with an exported function-hook variable, assigned from the dependent package's init() or manager constructor:

snapstate.ValidateRefreshes ← assigned by assertstate's delayed cross-manager init boot.HasFDESetupHook ← assigned by devicestate's manager constructor

or a registration mechanism, e.g. snapstate.AddCheckSnapCallback, snapstate.RegisterAffectedSnapsByAttr.

Also: almost everything under overlord is daemon-only and must not be imported by other snapd tools/binaries (it would bloat them significantly). The one sanctioned exception is the nomanagers-tagged subset of overlord/configstate/configcore.

In plain termsAssertions are small signed text documents that carry trust and policy: who published a snap, which revision is genuine, what a device model is. The root signing key is compiled into snapd itself, so verification works offline.

Assertions are signed documents carrying policy or verification data, implemented in the asserts package and persisted by overlord/assertstate.AssertManager. Key types:

Go deeper: where the root of trust actually lives, on-disk layout, and verification

The root of trust is embedded as literal Go source — not a file read at runtime, not fetched over the network. asserts/sysdb/trusted.go defines encodedCanonicalAccount and encodedCanonicalRootAccountKey as raw PGP-armored assertion text for the canonical authority, decoded via asserts.Decode(...) and compiled directly into the snapd binary. asserts/sysdb/generic.go embeds a second, parallel anchor (encodedGenericAccount, encodedGenericModelsAccountKey, encodedGenericClassicModel) used for the implicit "generic" classic-system model that an un-enrolled classic Ubuntu install gets.

On-disk storage (filesystemBackstore, asserts/fsbackstore.go): rooted at /var/lib/snapd/assertions/asserts-v0/, one subdirectory per assertion type name, then a path built from the type's primary-key header values. A stored filename can carry a .<formatnum> suffix when multiple assertion formats of the same assertion coexist on disk — pickLatestAssertion picks the highest format number the caller's snapd build actually supports, which is how format evolution stays backward-compatible with older snapd binaries reading the same assertion database.

Verification chain (CheckSignature, asserts/database.go):

  1. Confirms the assertion's authority-id matches the signing key's account, and that the key is scoped to be allowed to sign this assertion type at all (some account-keys are restricted to specific types).
  2. Verifies the actual signature cryptographically (OpenPGP-style) over the assertion's signed content.
  3. Cross-checks the assertion's sign-key-sha3-384 header — itself a fingerprint of the signing key — against the signing key actually used.
  4. Separately enforces the assertion's own timestamp header falls within the signing key's validity window — a validly-signed assertion can still be rejected for being outside the key's since/until bounds.

Every other account-key in the system must itself be signed by an already-trusted key before assertions it signs are trusted — a standard recursive chain rooted at the two embedded constants above, no separate revocation-list mechanism observed.

Sequence numbers: most assertion types (e.g. snap-revision) are immutable — their primary key fully identifies one eternal assertion, no "latest" concept, just presence/absence. validation-set is different: it's sequence-forming (AssertionType.SequenceForming()), modeled by AtSequence{Type, SequenceKey, Sequence} where Sequence <= 0 means "resolve to the latest" and a positive value pins to one specific point — printed as .../<n>. The on-disk format-number suffix scheme above is what lets multiple sequence points coexist simultaneously for resolution to choose among.

11 Install/refresh walkthrough, end to end

Tying Sections 5–10 together into one concrete, ordered story: snap install foo.

In plain termsEverything above, combined into one concrete story: what happens, task by task, when you run snap install foo — and how a refresh differs.

The real task chain built for one snap (snapInstallChoreographer, overlord/snapstate/snap.go). Click through the phases; tasks marked refresh only are skipped on a first install.

1. The request becomes a Change

snap install foo → POST /v2/snaps/foo → the daemon calls snapstate.InstallWithGoal(), which asks the store which revision to install (with the state lock released), checks conflicts and disk space, and returns a TaskSet. The daemon wraps it in a Change and answers 202 Accepted with the Change id. Nothing has been downloaded yet.

2. prerequisites → download-snap → validate-snap

  • prerequisites makes sure the snap's base and any default content providers are installed (or queues their installs) first.
  • download-snap fetches the .snap (resuming partial downloads, using a delta from the installed revision when possible, reusing the download cache) and checks its SHA3-384 hash. A local file uses prepare-snap instead.
  • validate-snap (assertstate) fetches the snap-declaration and snap-revision assertions and verifies the file against them — this is where store trust enters ().

3. mount-snap

Writes a systemd .mount unit for /var/lib/snapd/snaps/foo_42.snap → /snap/foo/42 and starts it. The new revision is now visible on disk but nothing uses it yet. Skipped if the revision is already present (e.g. a revert).

4. Refresh only: move the old revision out of the way

run-hook pre-refresh → stop-snap-services (honouring each service's refresh-mode; endure services keep running) → remove-aliases → unlink-current-snap. From here until step 6, the snap's apps are blocked from starting (the run-inhibit hint from ).

5. Prepare: kernel, gadget assets, data, security profiles

  • prepare-kernel-snap — kernels only: build the drivers tree (UC24+).
  • update-gadget-assets / update-gadget-cmdline — gadget and kernel snaps on Core: write boot assets ().
  • copy-snap-data — copy SNAP_DATA and every user's ~/snap/foo/<rev> from the old revision to the new one (skipped on revert).
  • setup-profiles — generate AppArmor/seccomp/mount/udev profiles for the new revision, before it becomes current, so it can never run unconfined.

6. link-snap — the point of no return (until undo)

Updates SnapState so this revision is current, flips the /snap/foo/current and /var/snap/foo/current symlinks, and writes wrappers: /snap/bin entries, systemd service units, D-Bus activation files, desktop files, icons. For a kernel, base or gadget on Core it also sets up the next boot and requests a reboot — the rest of the Change waits for it ().

7. auto-connect and aliases

auto-connect is the first task after a possible reboot: it connects every plug/slot the declaration policy allows to auto-connect () and regenerates profiles accordingly. Then set-auto-aliases and setup-aliases create command aliases ().

8. Hooks, then services

run-hook install (first install) or run-hook post-refresh (refresh) → quota-add-snap if a quota group was requested → run-hook default-configure (first install, applies gadget defaults) → start-snap-services. Services start only after the install hook has had a chance to set things up.

9. Finish

Refresh only: old revisions beyond the retain limit (refresh.retain) are discarded. Then run-hook configure and run-hook check-health. Finally, on a refresh, check-rerefresh may queue a follow-up refresh if the new epoch unlocked a newer revision ().

If any task fails, everything already done is undone in reverse — the snap ends up exactly as before.

Why the tasks are in this order

The order isn't arbitrary — each placement protects an invariant:

  • Verify before touching the system: download-snap and validate-snap finish before anything is mounted.
  • Confine before exposing: setup-profiles runs before link-snap, so there is never a moment where the new revision is current but has no security profile.
  • Connect after linking: auto-connect runs after link-snap (and after any reboot), because policy is evaluated against the snap that is actually current and booted.
  • Hooks before services: the install/post-refresh hook can prepare data and configuration before start-snap-services runs anything.
  • Symmetric undo: every task has an undo, so a failure at step 8 unwinds steps 7…1 and the system looks as if nothing happened.
Refresh vs. install: a refresh has the same shape, plus phase 4 (pre-refresh hook, stopping services, unlinking the old revision) and a final check-rerefresh; it keeps the old revision mounted (not discarded) until the new one is confirmed healthy, so snap revert stays cheap.
Go deeper: InstallWithGoal, the task "choreographer", and the refresh-busy pre-download path

snapstate.InstallWithGoal() (overlord/snapstate/target.go:862) is the real function behind step 1. It doesn't hardcode "install from the store" — it takes an InstallGoal interface whose toInstall() method resolves the actual snap(s) to install, which is how the exact same function drives a normal store install, a local sideload (--dangerous), and seeding () without three separate code paths. After resolving targets, it runs a disk-space check up front (checkDiskSpace) and, for a multi-snap batch (e.g. refreshing several snaps at once), assigns each target its own lane — the same lane mechanism from , here used so one snap's refresh failing in a batch doesn't take the others down with it.

For each target, doInstallOrPreDownload() (overlord/snapstate/snap.go:713) runs precondition checks (reserved name "system", disabled-snap rule, classic-confinement support, alias-conflict check), then asks shouldPreDownloadSnap() whether the snap is currently "busy" (running processes, refresh-app-awareness again, this time at the install-task-building layer rather than the launch-time layer from 's deep dive). If busy on an auto-refresh, instead of the normal task chain it builds a single pre-download-snap task and returns a distinguishable timedBusySnapError — the download happens now, but linking/switching over waits until the snap is actually idle.

Otherwise, a snapInstallChoreographer builds the real task chain via a taskChainBuilder, in named phases rather than one flat list: prerequisites (ensure base/content-providers are queued) → BeforeLocalSystemMod → a second synchronization prerequisites task → mount-snap (skipped entirely if this revision is already present on disk — e.g. a revert) → UpToLinkSnapAndBeforeReboot → AfterLinkSnapAndPostReboot. For essential snaps (kernel/base/gadget/snapd), SetEssentialSnapsRestartBoundaries then marks reboot coordination points on the chain — this is what lets snapd batch multiple essential-snap updates that each need a reboot into a single actual reboot instead of one per snap.

Go deeper: copy-snap-data, revert, and the home-directory migrations

copy-snap-data (backend.CopySnapData, overlord/snapstate/backend/copydata.go) does, for the system data dir and every user's ~/snap/foo:

  1. if a directory for the new revision already exists (e.g. from an earlier attempt), rename it to <rev>.old ("trash" it);
  2. recursively copy the old revision's directory to the new one, preserving ownership and permissions, with sync;
  3. on any failure, delete the partial copy and restore the trashed directory.

Undo deletes the new copy and restores the trash; the trash is only cleared after the Change succeeds. The consequence worth remembering: a revert does not carry newer data back — the old revision simply finds its own preserved directory, as it was when it last ran. That's what makes reverting after a bad data migration safe.

Go deeper: how a hook actually runs (HookManager.runHook)
  1. The task carries a HookSetup (overlord/hookstate/hookmgr.go): snap, hook name, revision, and flags — Optional (a missing hook is fine), IgnoreError, Timeout.

Configuration: snap set, snapctl and transactions

All snaps' configuration lives in one state key, "config" (snap → key → JSON). Changes go through a config.Transaction (overlord/configstate/config/transaction.go) that buffers changes on top of a snapshot and only writes them on Commit().

What happens on snap set foo a.b=c:

  1. The daemon calls configstate.ConfigureInstalled(), which creates a run-hook configure task carrying the patch {"a.b":"c"}.
  2. The configure handler's Before() creates the transaction and applies the patch to it (not to state).
  3. The snap's configure hook runs. Its snapctl get sees the uncommitted new values; it can validate them, adjust them with snapctl set, or exit non-zero to reject the change.
  4. Only if the hook succeeds does the transaction commit. A rejected change leaves configuration exactly as before.

System settings (snap set system …) use the same path for the special "core" snap, but the hook is hijacked by Go code in overlord/configstate/configcore that writes real system files (hostname, timezone, ssh, swap, watchdog, journal, proxies, refresh schedule…) — see .

  • Gadget defaults: a gadget's defaults: stanza (keyed by snap id) is applied on a snap's first install via UseConfigDefaults. If the snap has a default-configure hook it runs (before services start) to apply them; otherwise they go through the normal configure hook. System defaults are applied during seeding — and, for settings that only touch files, even earlier, at image build or in the initrd ().
  • Unset: snap unset foo a stores a null in the transaction; Commit() purges nulls.
  • confdb (confdb/, overlord/confdbstate) is a newer, separate mechanism: data shape and access are defined by a signed confdb-schema assertion with named views; several snaps can share data through views, with "custodian" snaps validating changes through change-view-*/save-view-* hooks. Data lives in a separate state key and is committed with dedicated commit-confdb-tx tasks.

0 Refreshes, the store & validation sets

How snaps keep themselves up to date without breaking running apps, how snapd talks to the store, and how fleets pin exact snap versions.

In plain terms
  • Four times a day (by default) snapd asks the store "anything newer?" and refreshes everything in one Change, one lane per snap.
  • If an app is running, snapd downloads the update but waits for the app to close (up to a limit) — refresh app awareness.
  • Refreshes can be held by users, the system, or the snaps themselves.
  • Validation sets are signed lists of snaps and exact revisions that a device must (or must not) have; snapd enforces them on every install, refresh and removal.

Auto-refresh: when snaps update themselves

Auto-refresh is a classic ensure-loop state machine () in overlord/snapstate/autorefresh.go. On each pass, EnsureAfterSeed():

  1. skips if the store is offline or the device isn't ready (a hook set by devicestate: e.g. not seeded yet);
  2. reads the schedule — refresh.timer (default 00:00~24:00/4: four random times a day), falling back to the legacy refresh.schedule;
  3. computes the next refresh time from the last one, and checks holds (refresh.hold) and metered connections (refresh.metered);
  4. when due, calls AutoRefresh(), which asks the store for updates to all snaps in one request, then re-checks the hold after re-taking the state lock, and creates one auto-refresh Change with each snap in its own lane.

On a freshly seeded device, the first auto-refresh is held for two hours (AtSeed()), giving setup tools time to finish. No snap can postpone refreshes beyond 95 days (maxPostponement).

Go deeper: catalog refresh and re-refresh

Catalog refresh (overlord/snapstate/catalogrefresh.go) is a separate daily job (24h + up to 6h random) that downloads store section names, the list of all snap names, and a commands.db used by command-not-found and snap advise-snap, into /var/cache/snapd.

Re-refresh: the last task of a refresh Change is check-rerefresh. Because the store only offers revisions whose epoch the installed revision can read (), crossing an epoch boundary may make an even newer revision available. check-rerefresh waits for the rest of the Change, then refreshes again only the snaps whose epoch changed.

Refresh app awareness: not pulling the rug from under running apps

Replacing a snap while its app is running can break it. snapd prevents this at two layers:

Soft check — when planning

For an auto-refresh, if any of the snap's processes are running (found via its cgroups), the snap gets only a pre-download-snap task: the update is downloaded now, then snapd watches the snap's cgroups (MonitorSnapEnded) and continues the refresh as soon as the last app exits.

Hard check — just before unlinking

After services stop, snapd re-checks and takes the snap's run-inhibit lock with a "refresh" hint. From then until link-snap, snap run waits (with a desktop notification) instead of starting the app ().

The wait isn't forever: once a refresh has been inhibited for refresh.max-inhibition-days (14 by default) it proceeds anyway. Users are told via a refresh-inhibit notice (), which desktop clients turn into notifications through the session agent.

Holding and gating refreshes

  • System-wide: snap set system refresh.hold=… postpones all auto-refreshes until a time.
  • Per snap, by the user: snap refresh --hold[=duration] foo (HoldRefreshesBySystem). Can be forever; --hold applies to auto-refresh only unless the hold level is "general".
  • By the snap itself (opt-in feature gate-auto-refresh-hook): before refreshing, snapd runs each affected snap's gate-auto-refresh hook, which can call snapctl refresh --hold or --proceed. The auto-refresh then splits into two phases: hooks first, then a conditional-auto-refresh task that refreshes only snaps nobody held. A snap's own holds are capped below the 95-day maximum.

Talking to the store

The store package is snapd's HTTP client for the Snap Store (or a brand/proxy store). The key pieces:

  • One batched call for decisions: Store.SnapAction() (store/store_action.go, endpoint v2/snaps/refresh) sends every installed snap's channel, revision, epoch, cohort and enforced validation sets, plus the requested install/refresh/download actions, and gets back what to fetch — optionally with the needed assertions.
  • Downloads (store/store_download.go): check the download cache (keyed by SHA3-384, in /var/lib/snapd/cache); try a delta (xdelta3 against the installed revision); otherwise download to .partial with resume support; always verify the SHA3-384 and retry once from scratch on mismatch.
  • Channels are track/risk/branch (risk = stable, candidate, beta, edge; snap/channel). Cohorts are opaque keys that make a group of devices see the same revision even while a release is rolling out.
Go deeper: authentication — user macaroons and device sessions
  • Users log in with snap login: the store returns a root macaroon plus an SSO discharge, sent with each user-specific request.
  • Devices authenticate with their identity: snapd fetches a nonce, signs a device-session-request assertion with the device key, sends it with the device's serial and model assertions, and receives a session macaroon used in a device-authorization header. This is how a brand store knows which devices may see its snaps — and why registration () matters even on classic.
  • The store package must not import the overlord, so it gets device information through the storecontext.DeviceBackend interface (implemented by devicestate). During a remodel, a different backend is swapped in so the store talks as the new model.
  • A proxy store is configured with snap set system proxy.store=<id> plus a matching signed store assertion carrying its URL.

Validation sets: pinning a fleet

A validation-set assertion lists snaps as required, optional or invalid, optionally at specific revisions. A device can track a set in two modes (overlord/assertstate/validation_set_tracking.go):

  • monitor — report compliance, change nothing;
  • enforce — refuse anything that would break compliance: installs or refreshes to non-allowed revisions, and removal of required snaps. Refresh requests tell the store about the enforced sets, so the store answers with compliant revisions.

snap validate --enforce first checks the installed snaps; if they don't comply, snapd can fix them automatically (install missing snaps, move to the required revisions) with an enforce-validation-sets task — but never removes snaps on its own. A model assertion can list validation sets too; those in enforce mode can't be forgotten, and seeding enforces them right after installing the seed's snaps ().

Epochs: protecting data-format changes

A snap's epoch declares which data formats a revision can read and write (snap/epoch.go). A refresh is only allowed if the new revision can read the current revision's epoch (checkEpochs), and the store only offers such revisions. Writing epoch: 2* means "I write format 2 and can still read format 1", which is how a publisher migrates data safely: first ship a revision that reads both, then one that only reads the new format. check-rerefresh walks devices across the boundary.

At link-snap, backend.LinkSnap() generates "wrappers" in a fixed order: binaries → services → D-Bus activation files → desktop files → icons (wrappers/).

  • /snap/bin: each non-service app gets /snap/bin/foo[.app] → /usr/bin/snap; snap run reads argv[0] to know which app was meant (). Apps with a completer: get bash completion.
  • Aliases (overlord/snapstate/aliasesv2.go): auto-aliases granted by the store in the snap-declaration, or manual snap alias foo.app name; both become /snap/bin/<alias> symlinks, with conflict checks across snaps and snap prefer to resolve them.
  • Desktop files from meta/gui/*.desktop are sanitized to an allow-list of keys and their Exec= rewritten to the /snap/bin wrapper, then installed into /var/lib/snapd/desktop/applications. Icons must be named snap.<snap>.*.
  • Session helpers (usersession/): the per-user session agent (user services, refresh notifications) and snap userd, which offers D-Bus services such as io.snapcraft.Launcher so a confined app can safely ask the desktop to open a URL or file.

Snapshots

snap save / restore / check-snapshot / forget (overlord/snapshotstate). A snapshot is a zip in /var/lib/snapd/snapshots/, e.g. 16_foo_1.2_42.zip, containing archive.tgz (system data: current revision + common), one user/<name>.tgz per user, and meta.json with hashes and the snap's configuration. Notices and warnings

Notices are snapd's event feed for clients (overlord/state/notices.go, overlord/notices). Types include change-update, refresh-inhibit, snap-run-inhibit, warning and the prompting types. Repeated events with the same type and key update one notice instead of creating many. Clients long-poll GET /v2/notices?after=…&timeout=… — unlike changes, this endpoint genuinely waits for new events.

Warnings (st.Warnf(...)) are a simpler user-facing mechanism shown by snap warnings and acknowledged with snap okay; they repeat at most daily and expire after 28 days.

Behind the experimental flag experimental.apparmor-prompting, interfaces like home, camera and audio-record can ask the user instead of silently allowing or denying. It needs kernel and AppArmor parser support.

  1. Interface snippets contain a ###PROMPT### marker which the AppArmor backend turns into the prompt qualifier when prompting is on.
  2. When a confined app hits such a rule, the kernel sends a request over /sys/kernel/security/apparmor/.notify; snapd's listener (sandbox/apparmor/notify) receives it.
  3. snapd checks stored rules; if they decide, it replies immediately. Otherwise it creates a prompt and an interfaces-requests-prompt notice.
  4. A desktop prompting client fetches /v2/interfaces/requests/prompts and replies allow/deny with a lifespan (once, session, timespan, forever) and path constraints; non-"once" replies become rules that can satisfy other pending prompts.

0 Ubuntu Core: where snapd and the OS meet

On Ubuntu Core, snapd isn't an add-on to the operating system — it is how the operating system is built, booted, updated, recovered and identified.

In plain terms
  • Everything is a snap: the root filesystem (base), the kernel, the device definition (gadget) and snapd itself.
  • A signed model assertion says which snaps make up the device and how locked-down it is.
  • The disk has four snapd-defined partitions: a read-only-ish seed of known-good systems, a small boot partition, a save partition for identity, and the encrypted data partition.
  • snapd code runs at every stage: building the image, inside the initrd, early in boot, as the daemon, and in independent repair tools.
The next four sections go deep: , , and .

The snaps that make a device

base (e.g. core24)

The root filesystem, booted read-only straight from its SquashFS. Updating the OS = refreshing this snap (with a try-boot).

kernel (e.g. pc-kernel)

Kernel + initrd (as one signed kernel.efi on UEFI), modules and firmware. Its initrd contains snapd's snap-bootstrap.

gadget (e.g. pc)

The device definition: partition layout (gadget.yaml), bootloader and its binaries, kernel command line, default configuration, pre-wired interface connections, registration hooks.

snapd

snapd itself, as a snap (since UC18). Refreshing it restarts the daemon; if the new one fails, snap-failure rolls back.

Which ones, from which publisher, in which channels, is fixed by the model assertion (asserts/model.go), signed by the device's brand. It also lists required and optional application snaps, validation sets, the grade, the store, and whether the system is classic (a hybrid system, see ).

The disk layout: four partitions, four jobs

The gadget's gadget.yaml assigns roles; snapd gives each role a fixed meaning. Click a partition:

  • Also the EFI System Partition: firmware boots shim and the recovery grub from here.
  • Holds recovery systems: systems/<label>/ (model, assertions, per-system files) plus shared snaps/. Each is a complete seed snapd can install or recover from.
  • Holds the recovery bootloader environment (snapd_recovery_mode, snapd_recovery_system) and FDE fallback keys (device/fde).
  • Created by image building, never re-created by install or factory reset. In the running system it's visible at /var/lib/snapd/seed and /run/mnt/ubuntu-seed.

ubuntu-boot — what to boot right now

  • The run grub, its grubenv (kernel_status, command-line variables), and the extracted kernel.efi per kernel revision, with kernel.efi/try-kernel.efi symlinks.
  • The sealed key that unlocks ubuntu-data in run mode (device/fde).
  • Mounted at /boot/grub in the running system. Re-created on factory reset.

ubuntu-save — what must survive a reset

  • The device's identity: serial assertion and device key (/var/lib/snapd/save/device), so a factory-reset device doesn't need to re-register.
  • FDE data for save, recovery-key material, and per-snap SNAP_SAVE_DATA directories.
  • Small, encrypted on FDE devices, and deliberately kept by factory reset.

ubuntu-data — the running system's writable state

  • system-data/ becomes the writable part of the root filesystem: /var/lib/snapd (state.json, installed snap files, assertions, modeenv), /var/snap, /etc overrides, home directories.
  • Encrypted with LUKS on FDE devices; unlocked in the initrd by snap-bootstrap.
  • Wiped and re-created by factory reset.

Optional extra roles exist for some bootloaders (raw bootloader images, an MBR, a u-boot environment partition system-boot-state), and system-seed-null for systems without a seed.

DeviceManager's job

overlord/devicestate.DeviceManager is the state manager orchestrating all of this. On classic systems its job is comparatively small: device identity for snap-store purposes. On Ubuntu Core it also:

  • Drives full device installation from a never-before-booted Core image, or a more limited installation of a snap set on first boot from a seed system.
  • Registers the device and gives it an identity — a serial assertion tied to the device's model assertion — with device services and/or the store.
  • Drives remodeling: transitioning a live device to a different model assertion (different brand/gadget/kernel/base/store), which is why task handlers that need device info must fetch a task-aware DeviceContext (snapstate.DeviceCtx(st, task, nil)) rather than a global one — mid-remodel, a task may need to see the new model, not the system's current one.

How classic and Core share one codebase

There's no separate "classic snapd" vs. "Core snapd" binary. The same overlord, same managers, same task kinds run everywhere. What actually changes behavior:

  • Which snaps are installed. A system without gadget/kernel/base snaps simply never exercises the Core-specific devicestate/boot task kinds — there's nothing for them to do.
  • release.OnClassic and friends — small runtime checks that steer specific decisions (e.g. interface auto-connection defaults in the declaration policy, 's on-classic constraints).
  • The asserts.Model assertion's fields (classic: true/false, grade, gadget/kernel/base references) describe which shape a given device is.
  • snapstate.DeviceContext is the interface snapstate defines to ask "what kind of device/model am I on" without importing devicestate back ('s acyclic-import rule in action) — concrete implementations come from devicestate.

Net effect: adding a Core-only feature almost always means adding new task kinds/handlers in overlord/devicestate (and maybe boot/gadget), not forking any shared code path.

Hybrid systems: a model with classic: true and kernel + gadget snaps (e.g. Ubuntu desktop with TPM-backed FDE) boots through the same grub → kernel.efi → snap-bootstrap path and gets recovery systems and FDE — but there is no base snap as root filesystem: ubuntu-data itself holds a normal classic root, ubuntu-seed is optional, and installation is driven by an external installer through the API (). In code: Model.HybridClassic(), and deviceCtx.IsCoreBoot() (the model has a kernel snap) vs. IsClassicBoot().

0 The Ubuntu Core boot process, stage by stage

From power-on to a running snapd on a UC20+ device — what happens at each stage, and exactly which parts are snapd's.

In plain terms snapd never runs "during" early boot as a daemon — but it is present at almost every stage anyway:
  • it wrote the bootloader configuration (grub.cfg) and the boot variables the bootloader reads,
  • it placed the kernel that gets booted,
  • its snap-bootstrap program runs inside the initrd and assembles the root filesystem out of snaps,
  • its systemd generators and units run early in the real system,
  • and once the daemon starts, it confirms the boot worked — which is what makes kernel and base updates safe to roll back.

Interactive boot timeline

Click a stage (or use Next/Previous). Each stage is colour-coded by who is running:

firmware bootloader (config written by snapd) kernel snap-bootstrap (snapd code in the initrd) systemd snapd daemon & helpers

1. Firmware loads shim from ubuntu-seed firmware

The UEFI firmware finds the EFI System Partition — on Ubuntu Core that is ubuntu-seed (vfat) — and loads EFI/boot/bootx64.efi, which is shim. With Secure Boot on, firmware verifies shim's signature, and each stage after this verifies and measures the next one into the TPM.

snapd's part: snapd put those files there. shim and grub come from the gadget snap and are treated as trusted assets: snapd records their hashes in the modeenv (CurrentTrustedRecoveryBootAssets), keeps copies in a cache (boot/assets.go), and only replaces them through an observed gadget update so FDE keys can be resealed first. On systems that support it snapd also writes the UEFI boot entry itself (UpdateBootEntry, via the UefiBootloader interface).

2. Recovery grub decides the mode bootloader

shim starts grub from ubuntu-seed, which runs EFI/ubuntu/grub.cfg — a file shipped inside snapd (bootloader/assets/data/grub-recovery.cfg, marked # Snapd-Boot-Config-Edition: 2). It reads two variables from the seed's grubenv:

  • snapd_recovery_mode — run, recover, install or factory-reset (unset means install: a factory-fresh image installs itself),
  • snapd_recovery_system — which recovery system (seed label) to use.

For run it simply chainloads the second grub on ubuntu-boot. For the other modes it loop-mounts the kernel snap file of the chosen recovery system (/systems/<label>/...) and chainloads its kernel.efi with snapd_recovery_mode=<mode> snapd_recovery_system=<label> on the command line. The recover entry first writes snapd_recovery_mode=run back, so recovery is one-shot: the next reboot returns to normal.

snapd's part: the config file itself, and the variables. snapd writes them when you ask for a mode switch (boot.SetRecoveryBootSystemAndMode — see ), and after install (EnsureNextBootToRunMode).

3. Run grub picks the kernel — or the try kernel bootloader

The second grub (ubuntu-boot, bootloader/assets/data/grub.cfg, edition 3) loads only three variables from ubuntu-boot/EFI/ubuntu/grubenv: kernel_status, snapd_extra_cmdline_args, snapd_full_cmdline_args. Then:

  • kernel_status=try → set it to trying, save, boot try-kernel.efi (a new kernel being tested);
  • kernel_status=trying → the last try never got confirmed (it crashed or hung): reset to empty and boot the old kernel.efi;
  • otherwise boot kernel.efi with snapd_recovery_mode=run plus the cmdline args.

snapd's part: kernel.efi and try-kernel.efi are symlinks snapd manages into per-revision directories like EFI/ubuntu/pc-kernel_123.snap/kernel.efi (EnableKernel/EnableTryKernel in bootloader/grub.go). Setting kernel_status=try is the very last thing a kernel refresh does before rebooting.

4. kernel.efi: kernel and initrd in one signed file kernel

kernel.efi is a Unified Kernel Image: the Linux kernel, the initrd and a small EFI stub (systemd's sd-stub) in a single signed EFI binary, built by the kernel snap's toolchain (core-initrd/*/bin/ubuntu-core-initramfs). Because the initrd is inside the signed, measured file, nobody can swap the early userspace without changing the measurements.

The kernel command line is composed by snapd (composeCommandLine in boot/cmdline.go): the bootloader's static arguments (e.g. panic=-1, consoles), plus the mode argument, plus whatever the gadget adds or removes (kernel-cmdline in gadget.yaml, or legacy cmdline.extra/cmdline.full). snapd stores the result in the boot variables above so grub only has to append it.

snapd's part: choosing which kernel file is current, extracting it from the kernel snap onto ubuntu-boot, and computing the command line.

5. In the initrd: find the boot disk snap-bootstrap

The initrd is a small systemd system (core-initrd/). A udev rule (90-ubuntu-core-partitions.rules) runs snap-bootstrap scan-disk on block devices. It identifies the disk the system booted from and creates stable symlinks: /dev/disk/snapd/{disk, ubuntu-seed, ubuntu-boot, ubuntu-data[-luks], ubuntu-save[-luks]}.

snapd's part: all of it — snap-bootstrap is a snapd binary (cmd/snap-bootstrap) with three subcommands: scan-disk, initramfs-mounts and recovery-chooser-trigger.

6. Mount partitions, unlock encryption, pick the snaps snap-bootstrap

snap-initramfs-mounts.service runs snap-bootstrap initramfs-mounts, the heart of early boot. In run mode (generateMountsModeRun):

  1. mount ubuntu-boot at /run/mnt/ubuntu-boot;
  2. measure the model assertion into the TPM (so keys only unseal for this model);
  3. mount ubuntu-seed at /run/mnt/ubuntu-seed (fsck'd every boot — it's a writable vfat);
  4. unlock ubuntu-data and ubuntu-save with the TPM-sealed key (or a recovery key/passphrase) and mount them at /run/mnt/data and /run/mnt/ubuntu-save;
  5. read the modeenv from data, and decide which base, gadget and kernel revisions to use (boot.InitramfsRunModeSelectSnapsToMount) — this is where a base try-update is handled, because grub can't read ubuntu-data: the initrd itself moves BaseStatus from try to trying (or falls back if it finds trying left over);
  6. check the kernel that actually booted is one the modeenv trusts; if not, reboot to fall back;
  7. mount the gadget and kernel snaps under /run/mnt/{gadget,kernel} and write a sysroot.mount unit for the base snap;
  8. on first boot only, mount the seed's snapd snap so it can run before anything is installed;
  9. finally, lock the sealed keys so nothing later in boot can unseal them again.

The other modes — install, recover, factory-reset — are covered in .

7. Assemble the root filesystem from snaps systemd snap-bootstrap

The root filesystem is the base snap's read-only SquashFS, mounted at /sysroot. Writable state is grafted on: sysroot-writable.mount binds the data partition to /sysroot/writable; the base's legacy writable-paths list is applied by an initrd script; and the-modeenv generates an fstab that binds ubuntu-boot/EFI/ubuntu to /boot/grub and ubuntu-seed to /boot/efi inside the final system.

The result: the "operating system" you boot into is literally a snap, and upgrading the OS means swapping which base SquashFS gets mounted here.

8. switch-root into the real system systemd

systemd's standard initrd-switch-root.target pivots into /sysroot. A snapd-provided unit (recovery-chooser-trigger-switchroot.service) carries one piece of state across: whether the user pressed the "recovery chooser" key during boot (see ).

9. systemd generators shipped by snapd snapd helpers

  • snapd-generator (cmd/snapd-generator, C): finds the kernel snap mounted by the initrd and generates early mount units for its modules/firmware (the kernel drivers tree, UC24+), and makes sure the root filesystem is a shared mount (needed for snap mount namespaces).
  • snapd-env-generator: adds /snap/bin to PATH.

10. Early units: mount every snap, load AppArmor snapd helpers systemd

  • Every installed snap has a generated .mount unit (written by snapd when the snap was installed — systemd/systemd.go) ordered before snapd.mounts.target. Kernel snaps' mounts are additionally ordered before udev and module loading.
  • snapd.apparmor.service loads all snap AppArmor profiles from disk before sysinit.target, so snap services can start confined without waiting for the daemon.
  • snapd.core-fixup.service (Core only) applies small fix-ups before snapd starts.
  • snapd.recovery-chooser-trigger.service watches for the recovery key on the console.

11. snapd.service starts snapd daemon

On Core, snapd runs from the snapd snap. The unit is Type=notify with a 5-minute watchdog and Restart=always. If a freshly-refreshed snapd keeps failing, OnFailure=snapd.failure.service runs snap-failure, which points /snap/snapd/current back at the previous revision and starts that instead ().

The daemon loads state.json, starts the managers () and enters the ensure loop.

12. snapd confirms the boot snapd daemon

On the first ensure-loop pass after each boot, DeviceManager.ensureBootOk() (overlord/devicestate/devicemgr.go) runs in run mode:

  1. it compares the current kernel boot id with the one it last handled — so it acts exactly once per boot;
  2. calls boot.MarkBootSuccessful(): a try kernel or base becomes the current one, boot-asset hash lists collapse to the new single value, tried recovery systems and a remodel's new model are committed;
  3. calls snapstate.UpdateBootRevisions(): if what actually booted differs from what snapd thought was current (because the bootloader fell back), it creates a change to revert its own records to match reality.

Only now is an update truly "done". This one step is what turns the bootloader's try/fallback mechanism into safe, automatic rollback — see .

Other architectures: the stages are the same with a different bootloader. Raspberry Pi uses piboot (the Pi firmware's own tryboot mechanism; snapd writes config.txt/tryboot.txt and extracts kernel, initrd and device trees), other ARM boards use u-boot (a boot.sel environment file) or Android-style lk. On those, step 3's try-logic is either in the bootloader's script or — for piboot — performed by snap-bootstrap in the initrd.

Go deeper: the Modeenv struct, and how try/current kernel-revision tracking survives a crash mid-update

Modeenv (boot/modeenv.go), persisted at /var/lib/snapd/modeenv on UC20+, is the ground truth for "what is this system actually booted into right now." Real fields include: Mode, RecoverySystem, CurrentRecoverySystems []string (systems currently being trusted/tried — the run key is resealed against all of these) vs. GoodRecoverySystems []string (vetted, fallback-ready — only these get the more conservative fallback key resealed against them), Base/TryBase/BaseStatus, CurrentKernels []string, the current Model/BrandID/Grade plus a parallel TryModel/TryBrandID/TryGrade set used during a remodel, and CurrentTrustedBootAssets (bootloader asset name → list of content hashes — two entries while an asset update is in flight, collapsing to one on success, which is literally how snapd detects whether a boot-asset update was applied without any extra state).

Crash-safe kernel promotion (UC20+, boot/bootstate20_bloader_kernel_state.go): a refresh sets bootenv kernel_status=try plus snap_try_kernel and a try-kernel.efi symlink; the boot script flips it to trying and boots the try kernel. On success, MarkBootSuccessful commits in a very specific, deliberate order: (1) clear kernel_status, (2) copy the try-kernel path into snap_kernel, (3) remove the try-kernel symlink last. The code comments spell out why: removing the symlink first would strand the system if the process were interrupted partway through the commit — the ordering is the actual crash-safety guarantee, not an implementation detail.

BootChain (boot/bootchain.go) — the measured-boot input — carries BrandID, Model, Grade, AssetChain []BootAsset, Kernel, KernelRevision, and KernelCmdlines. An empty KernelRevision means an unasserted (locally built/sideloaded) kernel — since snapd can't pin a specific trusted revision for it, this unconditionally forces a reseal rather than trying to diff revisions. PredictableBootChains (one chain per {model, recovery-system, kernel} combination) is what must stay unlockable for FDE to keep working ().

Managed boot config and trusted assets

Because grub.cfg decides what boots, an out-of-date config could leave a device unable to use a new snapd feature — or unable to boot. So snapd ships its own grub.cfg (embedded via bootloader/assets) and keeps the on-disk copy up to date:

  • Each shipped config starts with # Snapd-Boot-Config-Edition: N. UpdateBootConfig() rewrites the on-disk config only if it is snapd-managed (has the header) and has a lower edition. A config without the header belongs to the gadget and is left alone.
  • The update happens in the update-managed-boot-config task, added when the snapd snap is refreshed on a Core device and run late, so it's the new snapd that writes the new config.
  • Trusted assets — shim and grub binaries, provided by the gadget — are tracked by hash in the modeenv. During an update the old and new hashes are both listed (either may boot); after a successful boot the list collapses to the new one.
Why this is tied to FDE: changing grub.cfg, shim, grub or the kernel command line changes TPM measurements. That's why both update-managed-boot-config and update-gadget-cmdline are registered as resealing task kinds — the disk-encryption keys must be resealed for the new measurements before the reboot ().

core-initrd & snap-bootstrap

On Ubuntu Core 20+ (and non-Core Ubuntu configured to use a kernel+gadget snap), a systemd-based initrd defined per-Ubuntu-version under core-initrd/ is in use. Its main integration point is running snap-bootstrap (cmd/snap-bootstrap), which initializes and mounts the essential snaps needed to bring up the running system. Driven by the kernel command line, it supports distinct lifecycle modes:

installrunrecoverfactory-reset

This is the piece of snapd that runs before the daemon itself exists — it's doing its work from inside the initrd, assembling the root filesystem the rest of the system (including snapd) will boot into.

Go deeper: what each mode actually mounts, and "degraded mode"

Dispatch lives in cmd/snap-bootstrap/cmd_initramfs_mounts.go, one generateMountsMode<Mode> function per mode.

run mode (the hot path, every normal boot), roughly in order:

  1. Mount ubuntu-boot with a forced fsck — it's the first partition touched, so its integrity can't be assumed yet.
  2. Measure the model assertion into the TPM (idempotent, tracked via a stamp file so a restarted initrd run doesn't redo it).
  3. Mount ubuntu-seed — optional on classic (a "not found" error is swallowed only when the model is classic).
  4. Refresh bootloader environment variables now that boot/seed are visible.
  5. Unlock and mount ubuntu-data (and ubuntu-save if encrypted) via the TPM-sealed key.

install/recover/factory-reset share a common recoverModeStateMachine, parameterized by the mode string — recover and factory-reset literally run the same state machine, differing mainly in what happens to ubuntu-data afterward (recover: mount the existing data read-only under /host/ubuntu-data; factory-reset: wipe and recreate it). install mode is simpler and more linear — there's no existing encrypted data to unlock, just layout and format.

Degraded mode is tracked by a boolean flipped any time a partition fails to be found/mounted/unlocked with its primary key. The state machine then falls back partition-by-partition: a run-key unlock failure tries the fallback/recovery key; if ubuntu-boot can't be found at all, it falls back to keys sourced from ubuntu-seed instead. A healthy boot never touches any of these fallback branches.

Trust binding: snapd explicitly refuses to trust a mounted ubuntu-data unless it and ubuntu-save carry matching "from the same install" marker files — this stops an attacker from swapping in a different ubuntu-data to piggyback on a legitimately-unlocked ubuntu-save's secrets.

Two in-repo companions: cmd/snap-bootstrap/README.md walks through each mode's mounts, and cmd/snap-bootstrap/degraded-recover-mode.svg diagrams the recover/degraded-mode fallback decisions.

Updating the kernel or base: the try-boot cycle

A kernel, base or gadget refresh can't take effect without rebooting, and a bad one could leave the device unbootable. snapd handles this with a try / trying / commit cycle shared with the bootloader:

1. Prepare while the old system runs

The usual refresh tasks run (download, mount, …). For a kernel, prepare-kernel-snap builds its drivers tree and update-gadget-assets copies any boot assets the kernel provides (e.g. device trees). For FDE devices the keys are resealed so both the old and the new boot chain can unlock the disk.

2. link-snap sets the next boot

link-snap calls backend.MaybeSetNextBoot() → boot.Participant(...).SetNextBoot(). For a kernel this extracts kernel.efi, points try-kernel.efi at it and sets kernel_status=try; for a base it sets TryBase and BaseStatus=try in the modeenv. It returns "reboot required", and the task finishes with FinishTaskWithRestart(RestartSystem).

The Change is now paused across a reboot: later tasks in it (e.g. starting services, discarding the old kernel's setup) wait until snapd sees the reboot actually happened.

3. Reboot into the candidate

The bootloader (kernel) or snap-bootstrap (base) sees try, changes it to trying before booting the candidate, and boots it. Writing trying first is the safety net: if the candidate never gets far enough to be confirmed, the next boot will see trying still there.

4a. The new snap booted and snapd started

ensureBootOk() calls MarkBootSuccessful(): the try revision becomes current, kernel_status/BaseStatus are cleared, and the try-kernel.efi symlink is removed last (that ordering is deliberate crash-safety). The paused Change resumes; its next task's FinishRestart() checks that what booted is what was expected, and the refresh completes. discard-old-kernel-snap-setup then cleans up the previous kernel's drivers tree.

4b. The candidate failed to boot

A kernel panic (panic=-1 reboots immediately), a hang caught by a watchdog, or a power cut means snapd never confirms the boot. On the next boot the bootloader or initrd finds trying, clears it and boots the previous revision. When snapd starts:

  • FinishRestart() notices the booted revision isn't the one the refresh installed and fails the task — so the Change undoes its earlier tasks, exactly like any other failed operation ();
  • UpdateBootRevisions() reconciles snapd's records with what actually booted if they still disagree.

Net result: the device comes back on the old kernel/base, and snap changes shows the refresh as failed and reverted.

Go deeper: single reboot for several essential snaps, and the restart manager

One reboot, not three. If a refresh updates the kernel, base and gadget together, snapd marks restart boundaries on the tasks (SetEssentialSnapsRestartBoundaries) so all three are prepared and set to "try" before a single reboot.

How snapd asks for a reboot and knows it happened (overlord/restart/restart.go):

  1. restart.Request(st, RestartSystem, ...) records the current kernel boot id in state as system-restart-from-boot-id, and the Change is marked as waiting for a restart.
  2. The daemon schedules the reboot (by default with a 1-minute delay, or immediately for RestartSystemNow).
  3. After startup, the restart manager compares the stored boot id with the current one: different means the reboot happened and the waiting tasks may proceed; identical means it didn't, and snapd retries the reboot a limited number of times before giving up.

Restart kinds: RestartDaemon (snapd snap refresh), RestartSystem, RestartSystemNow, RestartSystemHaltNow, RestartSystemPoweroffNow, RestartSocket.

Switching modes: recover, reinstall, factory reset

A UC20+ device can boot into any of its recovery systems in a chosen mode. There are two ways in:

  • From the running system: snap reboot --recover (or --install, --factory-reset), or the /v2/systems API. snapd's switchToSystemAndMode() validates the system and mode, writes snapd_recovery_system and snapd_recovery_mode into the seed bootloader's environment, and requests an immediate reboot.
  • At the console during boot: snap-bootstrap recovery-chooser-trigger watches input devices for a trigger key for a few seconds and, if pressed, leaves a marker file. Later, snap-recovery-chooser (a snapd tool) shows a menu (via console-conf) of systems and actions, and posts the choice to the API — which then follows the same path as above.

How UC16 and UC18 boot differently

Older Ubuntu Core has no snap-bootstrap, no modeenv, no recovery systems and no FDE: one writable partition plus a boot partition, and a script-based initrd. UC16 boots the all-in-one core snap (OS and snapd together); UC18 introduced separate core18 base and snapd snaps. The code picks the right implementation via bootStateFor(), depending on whether the device has a modeenv.

0 Building and installing a Core device

From a model assertion on a developer's machine to a device that has installed, seeded, and registered itself.

In plain terms
  1. Build: snap prepare-image (usually via ubuntu-image) downloads the model's snaps and assertions and writes a seed onto what will be ubuntu-seed. The image is set to boot in install mode.
  2. Install: on first power-on, snapd runs from a temporary in-memory system, partitions and (optionally) encrypts the disk, sets up run mode, and reboots.
  3. Seed: in run mode, snapd installs the seed's snaps into the real system, then registers the device.
The seed stays on ubuntu-seed as a recovery system, ready for recover mode, reinstall, or factory reset.

Building an image: snap prepare-image

image.Prepare() (image/image_linux.go) is the library behind snap prepare-image and used by ubuntu-image:

  1. Decode the model assertion (or use the generic classic model for --classic), check architecture and series.
  2. Create a tooling store client scoped to the model's store; read extra assertions (only system-user is allowed as an extra, and only for grade dangerous).
  3. Resolve local snaps, then download every needed snap and its snap-declaration/snap-revision through seedwriter.Writer, choosing assertion formats the seeded snapd can parse.
  4. Check that the seeded snapd is compatible with the snap-bootstrap in the seeded kernel's initrd, check validation sets, copy snaps, write metadata.
  5. Unpack gadget and kernel, validate gadget content, and call boot.MakeBootableImage(). For UC20+ this installs the recovery grub config and sets snapd_recovery_mode=install + snapd_recovery_system=<label> — so the image's first boot is an install.

The recovery-system label defaults to the build date (YYYYMMDD). For UC16/18, image building instead writes a classic seed.yaml seed into the future writable partition and points the bootloader at the kernel and core directly.

What a seed looks like

UC20+ (seed/seed20.go)

ubuntu-seed/
  snaps/                 # asserted snaps, shared
  systems/20261104/
    model
    assertions/model-etc
    assertions/snaps
    snaps/               # local/unasserted (dangerous)

UC16/18 (seed/seed16.go)

/var/lib/snapd/seed/
  seed.yaml

One seed only, consumed once at first boot; no recovery systems.

Code reads seeds through the seed.Seed interface (seed/seed.go): seed.Open(dir, label) returns the right implementation; LoadAssertions() imports them into a database; LoadMeta(mode) resolves snaps; EssentialSnaps() and ModeSnaps(mode) split them. Each snap in the model has a list of modes it's needed in: essential snaps default to run + ephemeral (install/recover/factory-reset), others to run only — which is how an install or recovery system stays minimal.

Grades constrain seeds: above dangerous, no local/unasserted snaps, no channel overrides, no devmode, no extra snaps; classic-confined snaps must be explicitly allowed by the model.

Preseeding: doing first-boot work at build time

Seeding on first boot mounts every snap, generates all security profiles and units — slow on small devices. Preseeding runs snapd at image-build time in a chroot (SNAPD_PRESEED=1, image/preseed) so that work is already done:

  • seeding proceeds normally, but a mark-preseeded task is spliced in before every snap's hooks ();
  • when it runs, snapd unmounts the snaps, records preseeded=true plus the system key, and stops — leaving a state.json with all the hook-and-later tasks still pending;
  • for UC20+, the resulting writable data is packed into systems/<label>/preseed.tgz with a signed preseed assertion; install mode unpacks it into ubuntu-data after checking the signature;
  • on the real first boot, the paused Change simply continues with the hooks.

snap-preseed --reset undoes preseeding of a classic chroot, using the snapd inside the image so the reset matches that version's file layout.

Install mode, step by step

1. The image boots in install mode

The recovery grub finds snapd_recovery_mode=install (set at image build) and boots the recovery system's kernel with snapd_recovery_mode=install snapd_recovery_system=<label>.

2. snap-bootstrap builds a temporary system

It mounts ubuntu-seed, verifies the recovery system's essential snaps against its assertions, mounts base, kernel, gadget and snapd from the seed under /run/mnt/, and creates a tmpfs root for writable data with an ephemeral modeenv (Mode=install). Gadget system defaults that only touch files are applied here. Nothing on the disk except ubuntu-seed exists yet.

3. snapd seeds the ephemeral system

snapd starts in the tmpfs system and seeds only ModeSnaps("install") (essential snaps, plus anything the model marks for install mode). Then ensureInstalledAfterSeed() (overlord/devicestate/devicemgr.go) creates the "Install the system" Change: setup-run-system → [setup-ubuntu-save → run-hook install-device] → restart-system-to-run-mode. The installer is snapd itself, using the same task machinery as everything else.

4. setup-run-system: partition and encrypt

doSetupRunSystem (overlord/devicestate/handlers_install.go) decides whether to encrypt (TPM availability vs. the model's storage-safety: secured requires it), validates the gadget, then calls gadget/install.Run() with the state lock released:

  • find the boot disk and check the existing partition table is compatible with the gadget;
  • create the missing partitions — only system-boot, system-save, system-data are ever created; ubuntu-seed came from the image;
  • LUKS-encrypt save and data if needed, create filesystems, write gadget content.

5. boot.MakeRunnableSystem()

  • copy the base, kernel and gadget snap files into ubuntu-data;
  • write the run-mode modeenv: Mode=run, RecoverySystem=<label>, current and good recovery systems = [label], trusted asset hashes, kernel, model;
  • on ubuntu-boot: install the run grub config, extract kernel.efi, enable it, set the command-line variables;
  • with encryption: seal the data/save keys against the boot chains (run key on ubuntu-boot, fallback key on ubuntu-seed);
  • mark the recovery system as good on the seed.

6. The gadget's install-device hook (optional)

Runs with the new system prepared but not yet booted — e.g. to provision device-specific files. It can call snapctl reboot --halt or --poweroff to change what happens at the end (useful on a factory line).

7. restart-system-to-run-mode

If the seed has a preseed.tgz, it's verified and unpacked into ubuntu-data. Then boot.EnsureNextBootToRunMode(label) writes snapd_recovery_mode=run into the seed's grubenv — this single write is the switch to run mode — install logs and timings are copied to ubuntu-data, and snapd requests an immediate reboot. The next boot follows the run-mode path in , and seeding continues in .

For per-mode initrd details, cmd/snap-bootstrap/README.md in the repository is a good companion.

Seeding: how a system installs itself on first boot

Seeding is how a brand-new system — a freshly flashed Ubuntu Core image, or a classic system configured with a seed — gets from "empty state" to "every required snap installed, confined, and configured" entirely on its own, driven by the ensure loop rather than any user action.

  1. Trigger: DeviceManager.ensureSeeded() (overlord/devicestate/devicemgr.go:1110) runs on every ensure-loop pass. It first checks the "seeded" state key — once true, it's a permanent no-op for the life of the system.
  2. Build the task graph: populateStateFromSeedImpl() (overlord/devicestate/firstboot.go:161) does the real work — read on to see exactly how.
  3. Run it: the resulting []*state.TaskSet is wrapped into a Change and executed exactly like any other operation — same TaskRunner, same lanes, same undo contract from .
  4. Completion: a mark-seeded task sets "seeded" = true once everything finishes, which is what flips ensureSeeded() off for good.
Go deeper: populateStateFromSeedImpl(), task by task, with the actual lane/ordering logic

Reading overlord/devicestate/firstboot.go top to bottom, the real sequence is:

  1. Guard: refuses if "seeded" is already true.
  2. Resolve mode: seedLabelAndMode() — if there's a modeenv, this is a UC20+ boot mode (install/recover/…); otherwise defaults to "run" (classic/UC16-18 shape).
  3. Import assertions: importAssertionsFromSeed(mode, isCoreBoot) acks every assertion the seed carries into the local database () — model, snap-declarations, snap-revisions, account-keys, etc. If there's genuinely nothing to seed, short-circuits to trivialSeeding() (a classic system with no pre-seeded snaps is a valid, if boring, seed).
  4. Load snap metadata: deviceSeed.LoadMeta(mode, ...) — reads seed.yaml/model-derived snap lists and resolves them to real *snap.Info plus *state.TaskSet per snap, via installSeedSnap() which calls the exact same snapstate.InstallOne path a normal install uses, with Seed: true and NoDelayedSideEffects: true set on the options.
  5. Two separate lanes, on purpose: essential snaps (base/kernel/gadget/snapd — essentialLane := st.NewLane()) and non-essential snaps (nonEssentialLane := st.NewLane()) get different lanes. The comment is explicit about why: if installing an optional seeded snap fails, that must not undo the essential snaps that already succeeded — seeding partially-but-safely is preferable to failing the whole boot over one optional app.
  6. Ordering matters for hooks: chainSorted() stable-sorts essential snaps so the boot base installs before the kernel — specifically so any kernel hook has a working rootfs (the base) to execute against when it runs. Snap type ordering is expressed via effectiveType(info).SortsBefore(...), with the model's base snap given a synthetic InternalTypeBootBase type purely to make this ordering explicit.
  7. Configure after install, not interleaved: core/kernel/gadget each get a ConfigureSnap(..., UseConfigDefaults) taskset, chained to run only after all essential snaps are installed — so gadget-provided config defaults are available by the time anything is configured, rather than each snap configuring itself in isolation.
  8. Preseeding is a distinct sub-mode: if m.preseed is set (building a snap image ahead of time, not an actual first boot), a mark-preseeded task is spliced in between each snap's preliminary setup and its hooks (via the taskset's BeginEdge/BeforeHooksEdge/HooksEdge markers) — hooks are made to wait for it, and it waits for every snap's pre-hook setup, so no hook runs before the whole system is in its preseeded state.
  9. Validation sets: after installing everything, maybeEnforceValidationSetsTask() adds a task to start tracking any validation-sets bundled in the seed — but only in run mode, and only in the non-essential lane (a comment notes undoing the essential lane doesn't currently work properly, so validation-set enforcement failures are deliberately scoped to not cascade into essential-snap rollback).
  10. Final task: markSeededTask() waits on literally everything (the last snap's taskset and the end-taskset), then sets "seeded" = true and records a seed-system entry (label, model, brand, revision, timestamp) describing exactly which seed produced this system — this is what a later snap debug seeding-style introspection reads back.
Why two lanes instead of one flat list: this is the clearest real-world illustration of 's lane mechanism in the whole codebase — essential vs. non-essential seeding is lanes solving exactly the problem they exist for: one failure domain (an optional app) must not be allowed to take down another (the device's own bootable base).

Installer-driven installs (desktop and hybrid)

An external installer (e.g. the Ubuntu desktop installer for TPM-backed FDE) drives the same building blocks step by step through POST /v2/systems/{label} with "action": "install" (daemon/api_systems.go):

  1. GET /v2/systems/{label} — model, gadget volumes and encryption availability.
  2. step: setup-storage-encryption — task install-setup-storage-encryption encrypts the partitions the installer created. A passphrase or PIN is kept only in memory (st.Cache), never written to state.
  3. generate-recovery-key — optional pre-install recovery key.
  4. step: finish — task install-finish merges the installer's partitioning into the gadget, writes content, copies the seed onto the new ubuntu-seed (seed.Copier), seals keys and makes the system bootable.
  5. optionally install-preseed, running snap-preseed --hybrid on the target root.

Recovery systems: creating and testing new known-good systems

The seed shipped in the image doesn't have to be the only one. snap recovery lists systems; POST /v2/systems with action: create builds a new one from the snaps currently installed (or required by validation sets) — e.g. to capture an updated, tested state as a new recovery point.

  1. create-recovery-system writes systems/<label> (and any new shared snaps) to ubuntu-seed, logging every new file so a failure can remove exactly what it created.
  2. If the system is to be tested (requested by the caller, and always the case for a remodel), snapd marks it as try (try_recovery_system, recovery_system_status=try in the seed env), adds it to the modeenv's current recovery systems, reseals keys, and reboots into it in recover mode.
  3. In that test boot, snap-bootstrap checks it can reach the real data (using only the run key, no fallback), marks it tried, and immediately reboots back to run mode.
  4. Back in run mode, ensureTriedRecoverySystemAfterSeed() reads the outcome; finalize-recovery-system promotes it to a good recovery system (the fallback key is now sealed for it too) and optionally makes it the default.

The default recovery system is what snap reboot --recover/--factory-reset/--install use when no label is given. Systems in use can't be removed; snapd works out which shared snaps become unused.

Factory reset: wipe everything except identity

snap reboot --factory-reset [label] reboots into factory-reset mode:

  1. snap-bootstrap deliberately ignores ubuntu-boot and ubuntu-data (they may be why you're resetting) and unlocks only ubuntu-save, using the fallback key from ubuntu-seed. It then builds an ephemeral system like install mode.
  2. snapd seeds it and runs factory-reset-run-system: install.FactoryReset() re-creates only system-boot and system-data; system-save is kept.
  3. It finds the serial assertion whose device key is still in ubuntu-save and copies the model and serial into the new ubuntu-data — this is how the device keeps its identity without re-registering.
  4. It makes the new system runnable, reseals keys, leaves a factory-reset marker, and reboots to run mode.
  5. In run mode, snapd verifies the marker, rotates the ubuntu-save key, removes the marker, and restores the serial and key from save instead of requesting new ones.

0 Running a Core device: gadget, kernel, identity, configuration

What snapd does over a device's life: updating boot assets, kernels and itself, registering the device, configuring the OS, creating users, and repairing it if all else fails.

In plain terms
  • Gadget and kernel refreshes can rewrite boot partitions — carefully, with backups, only when the gadget says a structure's edition increased.
  • A refreshed snapd restarts itself; if it fails to start, snap-failure puts the previous one back.
  • Each device gets an identity — a serial assertion — from a device service, driven by the gadget's prepare-device hook.
  • snap set system … is how the OS is configured on Core, since /etc isn't freely editable.
  • snap-repair can run signed emergency scripts even if snapd itself is broken.

The gadget snap: layout, assets and updates

gadget.yaml is parsed into gadget.Info (gadget/gadget.go):

  • volumes → structures (partitions or raw areas), each with a role, size, offset, type, filesystem, content (files to copy, or raw images), and an update stanza with an edition number;
  • defaults (configuration for snaps, by snap id, including system);
  • connections (interface connections made at seeding);
  • kernel-cmdline (append/remove/allow; legacy cmdline.extra/cmdline.full files).

Gadget hooks: prepare-device and prepare-serial-request (registration), install-device (install mode).

Go deeper: how a gadget refresh updates boot assets (gadget.Update)

A gadget or kernel refresh on Core adds an update-gadget-assets task (overlord/devicestate/handlers_gadget.go), which calls gadget.Update() (gadget/update.go):

  1. Old and new layouts must describe the same volumes; structure sizes, offsets and types must be compatible.
  2. Policy decides which structures to touch: by default only those whose update.edition increased; during a remodel, everything but the MBR; for a kernel refresh, only content that comes from the kernel ($kernel: references, e.g. device trees).
  3. Order: boot-partition structures first, then seed — the newest binary in the boot chain is updated first.
  4. Every updater first backs up what it will change into a rollback directory; any backup failure cancels. Then each writes (raw structures are written at device offsets; filesystem structures file by file, honouring preserve). On failure, all attempted updates are rolled back.
  5. The update is wrapped by the FDE trusted-assets observer, so changing shim/grub triggers resealing before the reboot that will use them.
  6. The task requests a system restart.

update-gadget-cmdline applies kernel command-line changes the same way: compute the new line, update the boot variables, reseal, reboot. Arguments like root=, init= or most snapd* arguments are rejected.

The kernel snap: drivers tree, modules and reboots

  • kernel.yaml (kernel/kernel.go) declares assets the gadget may consume (e.g. dtbs, with update: true) and dynamic-modules for modules generated at runtime.
  • Drivers tree (UC24+, kernel/kernel_drivers.go): rather than using the kernel snap's /lib/modules directly, snapd builds /var/lib/snapd/kernel/<name>/<rev> combining the kernel's modules/firmware with any kernel-modules components, runs depmod, and the system bind-mounts it on /usr/lib/{modules,firmware}. Task: prepare-kernel-snap.
  • Installing or removing a kernel-modules component rebuilds the live tree atomically (build alongside, then swap) — new modules without a reboot.
  • A kernel refresh needs a reboot: the running kernel can't be swapped. link-snap makes it the try kernel and requests a restart (); after the reboot, discard-old-kernel-snap-setup removes the previous revision's drivers tree (never the current one).

The base and snapd snaps: updating the OS and snapd itself

The boot base is the base named in the model. It participates in boot on non-classic models, so its refresh works exactly like a kernel's: TryBase/BaseStatus=try in the modeenv, reboot, confirm or fall back (handled in the initrd, since bootloaders can't read the modeenv).

The snapd snap restarts the daemon instead of the system:

  1. link-snap for the snapd snap requests RestartDaemon; the new snapd starts and continues the same Change.
  2. Later tasks call FinishRestart(), which waits for the restart, regenerates snapd's own systemd units (the new binary may generate them differently), and fails if a rollback happened meanwhile.
  3. On Core, an update-managed-boot-config task lets the new snapd refresh grub.cfg ().
Go deeper: snap-failure — recovering from a snapd that won't start

snapd.service has OnFailure=snapd.failure.service, which runs snap-failure snapd (cmd/snap-failure/cmd_snapd.go). It deliberately imports almost nothing from snapd:

  1. read /var/lib/snapd/sequence/snapd.json to find the previous snapd revision;
  2. stop snapd.socket, point /snap/snapd/current back to the previous revision;
  3. run that snapd with SNAPD_REVERT_TO_REV=<rev> — it recognizes the situation (CheckExpectedRestart) and fails the refresh Change so it undoes cleanly;
  4. wait for the sockets to become active; otherwise reset and restart the units, retrying once.

Registration: how a device gets its identity

After seeding in run mode, ensureOperationalAfterSeed() (overlord/devicestate/devicemgr.go) creates an "Initialize device" Change if the device has no serial yet:

  1. run-hook prepare-device (gadget, optional): sets device-service.url, extra headers, a registration.proposed-serial, or device-service.access=offline via snapctl set.
  2. generate-device-key: a 4096-bit RSA key, generated with the state lock released. On UC20+ it's stored on ubuntu-save.
  3. request-serial: get a request id from the device service (the store by default, or the brand's serial vault), build a serial-request assertion signed with the device key, post it, and receive the serial assertion. Retries handle no network, a clock not yet set (certificates "not valid yet"), and 5xx errors; 4xx errors fail with the server's message.

The serial plus model are then used to open a device session with the store (). Classic systems with no model get the built-in generic/generic-classic model and register the same way. Failed attempts back off from 5 minutes up to 24 hours.

The filesystem-only handlers are also compiled into snap-bootstrap and the image builder (the nomanagers build tag keeps the state-dependent ones out), so a gadget's system defaults can be applied before snapd ever runs — at image build or in the initrd.

The first user: system-user assertions and console-conf

  • console-conf (outside snapd) offers network setup and SSO-based user creation on the console. It calls POST /v2/internal/console-conf-start so snapd delays auto-refreshes while it runs.
  • system-user assertions let a brand pre-authorize users. snap auto-import (triggered by udev) scans removable media for auto-import.assert, imports it, and asks snapd to create users automatically. snapd checks the assertion is signed by an authority listed in the model, matches the model and series, and — if bound to serials — waits until the device has its serial.
  • Once any user exists the device is managed (reported in /v2/system-info) and automatic user creation stops.

snap-repair: the last line of defence

snap-repair (cmd/snap-repair) exists for the case where snapd itself is broken in the field. A systemd timer runs it a few times a day; it fetches repair assertions — signed scripts — in sequence, checks whether each applies (series, architectures, models, bases, modes), and runs applicable ones with a 30-minute timeout. The script reports repair done|skip|retry.

It is intentionally independent: its own binary, timer, HTTP client, state, and its own embedded root key (it doesn't trust snapd's assertion database), so it keeps working whatever state snapd is in. It runs only on Core.

Remodeling: changing a live device's model assertion

Remodeling moves a live, already-seeded device to a different model assertion — different gadget/kernel/base/store/brand — without reflashing. Handlers live in overlord/devicestate/handlers_remodel.go and remodel.go; this is the scenario that makes the task-aware DeviceContext (see ) necessary, since a task mid-remodel may need to see the new model rather than the system's current one.

Go deeper: the three kinds of remodel, the pre-flight checks, and how the task graph differs per kind

ClassifyRemodel(oldModel, newModel) (devicestate/remodel.go:85) sorts every remodel into exactly one of three kinds, decided purely from assertion header comparisons:

KindConditionWhat changes
UpdateRemodelsame brand + modelJust a revision bump of the same model (e.g. a new required-snaps list) — same brand store.
StoreSwitchRemodelsame brand + model, different Store()Needs a fresh store session (sto.EnsureDeviceSession(), with the state lock released around the network call) before falling through to build the same task graph as an update.
ReregRemodeldifferent brand ID or different model nameThe device needs a brand-new identity: a request-serial task runs first, then prepare-remodeling — a much smaller initial taskset than the other two kinds, since the rest of the remodel's tasks get added later, inside a task, once the new serial exists.

Remodel() (devicestate/devicestate.go:1456) runs a long pre-flight gauntlet before building anything, each a hard rejection:

  • Refuses if the device isn't fully seeded yet, or if an online remodel was given local snap/component paths (those require --offline).
  • The new model's revision can't be older than the highest revision of that model already known to the device — no silent downgrades.
  • Requires an existing serial assertion, with one narrow exception: an offline, same-brand UpdateRemodel is allowed without one.
  • Refuses a series change, a classic-boot device, crossing classic↔non-classic, crossing grade (except the specific pre-UC20→UC20+ case, which gets its own explicit rejection message), losing a base snap (UC18+→UC16 backslide), or an architecture change.
  • Calls snapstate.CheckChangeConflictRunExclusively(st, "remodel") — remodels are exclusive: nothing else gets to run concurrently with one (a stronger guarantee than the ordinary per-snap conflict check from ).

Because a StoreSwitchRemodel has to release the state lock to establish a new store session, Remodel() re-validates after reacquiring it — re-reads the current model and checks it still matches what the function started with, and re-checks no other remodel Change snuck in — the exact same "re-validate mutable state after the lock gap" pattern as and the conflict race-check in 6.5, applied here at the top of a much bigger operation.

Finally: chg := st.NewChange("remodel", msg), a remodelContext is cached onto the Change itself (remodCtx.Init(chg)) so every task handler in the remodel can look up kind-specific behavior (via remodelCtxFromTask) without having to re-derive it, and every built taskset is added to the one Change.

0 Full disk encryption

How snapd ties the data partition's encryption to the exact software that boots — and keeps it working through every update.

In plain terms The key that unlocks ubuntu-data is sealed by the TPM: the TPM only releases it if the boot chain (shim, grub, kernel, command line, model) measured during this boot matches what snapd sealed it for. So whenever snapd is about to change any of those, it must reseal first — for both the old and the new chain — or the device wouldn't be able to unlock its own disk after the reboot.

Which keys exist, and where they live

File names are defined in gadget/device/encrypt.go. Key slots are managed by overlord/fdestate.FDEManager, with task kinds such as fde-add-recovery-keys, fde-remove-keys, fde-rename-keys, fde-add-platform-keys, fde-change-auth, and the secure-boot database update pair efi-secureboot-db-update-prepare/efi-secureboot-db-update. Devices without a TPM can implement encryption through the kernel snap's fde-setup hook (e.g. OP-TEE on ARM).

Full Disk Encryption

snap-bootstrap is also central to FDE support, tying encryption to the specific device via TPM+UEFI, OP-TEE on ARM, or hooks for other TEEs — obtaining device-protected keys from those security modules to unlock encrypted disks. Low-level helper logic lives in secboot (a wrapper around the external secboot package).

Because TPM-based FDE requires measuring boot assets to unseal keys, the implementation must stay in sync with the update logic for essential snaps — any update to kernel/base/gadget changes the measurements. Both boot and the dedicated overlord/fdestate.FDEManager carry the logic for keeping key-sealing policy consistent with the snaps currently/about-to-be booted.

Go deeper: what gets measured, what triggers a reseal, and recovery keys vs. the TPM path

What's measured: secboot/secboot_tpm.go reserves initramfsPCR = 12 for "EFI image" measurements. Both the system epoch and the model assertion's identity itself are measured into PCR 12 — not just binaries — so a remodel necessarily changes the PCR value and forces a reseal. PCR policy-counter handles are fixed, pre-reserved TPM NV indices, with separate RunObjectPCRPolicyCounterHandle/FallbackObjectPCRPolicyCounterHandle and a parallel Alt... pair — the "Alt" handles exist specifically so a factory-reset can rotate to the alternate counter rather than reuse (and potentially replay-attack) the original one.

What triggers a reseal (resealExpectedByModeenvChange, boot/seal.go): essentially any Modeenv diff — kernel/base try→current promotion, recovery-system list changes, trusted-boot-asset hash changes, model/try-model changes (remodel), kernel command-line changes — except a gadget-field-only change, which is deliberately excluded here because gadget/boot-asset changes are already caught separately via content-hash diffing elsewhere, avoiding a redundant double-trigger.

Recovery key vs. the main flow: the normal run-mode unlock uses a TPM-sealed key gated by the current PCR policy — it only unseals if the measured boot state (kernel/model/bootloader chain) matches exactly. The recovery key is a wholly separate, human-enterable key not bound to PCR state at all — the fallback path when the measured chain can't be verified (new/failed kernel, tampered bootloader, hardware change) or when ubuntu-boot itself can't be mounted (the initramfs degraded-mode fallback above). It's managed as a first-class keyslot alongside the TPM-sealed "platform" keys, with its own add/remove/rename task kinds in FDEManager.

overlord/fdestate's check-reseal task is a verification gate, not a scheduler — it validates that resealing is in the expected state (commonly run after a restart); the actual resealing happens inline inside the state-changing handlers themselves (adding a platform key, changing auth, a secure-boot DB update). Two devicestate-owned task kinds, install-setup-storage-encryption and fde-reprovision, are explicitly registered as "this changes sealing-relevant state" even though they live outside fdestate — another example of the registration-hook pattern from .

14 Conventions & validation

The project-specific rules that make a diff look like it belongs in this codebase.

Naming & errors, condensed

  • Follow gofmt -s and standard Go naming conventions; prefer concision for locals, clarity for exported names; stay consistent with neighboring code's terminology.
  • Error messages: start lowercase, no trailing period, prefer "cannot …" over "failed to …", avoid repeated "cannot: cannot:" when errors get wrapped, and prefix genuine programming errors with "internal error: ".
  • Don't introduce an exported *Error type until a caller actually needs to inspect it.
  • Package layout: a responsibility split across packages should go from higher- to lower-level abstraction (e.g. snapstate → snapstate/backend → boot → bootloader), not splitting the same abstraction level across packages.

Testing conventions

  • Prefer tests in a dedicated <package>_test package, exercising the exported API; reach for export_test.go re-assignment only when internals genuinely need covering.
  • snapd tests use gocheck plus the project's own testutil; benchmarks use the standard testing package.
  • Mocking convention: Mock* helpers in export_test.go, each returning a parameterless restore function.
  • For task handlers specifically: test that undo correctly reverses do, that handling is idempotent under partial execution, and that error paths undo previous state as needed ('s checklist).
